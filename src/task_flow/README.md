Status: v1 设计稿（评审后修订）

## 一、定位与目标

### 1.1 解决什么问题

1. **同类任务执行发散**：同一类任务每次做，步骤、质量、产出形态都不稳定，用户难以验收结果。
2. **子智能体委派率低**：目前绝大多数任务由主 Agent 独自完成，SubAgent 很少被委派。任务流把"什么时候该委派、委派给谁"固化在流程定义里（步骤级执行者 + 并行子流默认委派），让并行执行成为机制而非偶发行为。

手段不是写死规则，也不是全塞进 Prompt，而是：用户充当任务指导者，提前定义任务执行流程；Agent 执行任务时若命中已有任务流，就按统一方法执行。

### 1.2 两类任务流，同一套引擎

| 类型 | 来源 | 存储 | 可编辑性 |
|:--:|:--|:--|:--|
| 内置流（builtin） | 系统随版本发布，作为底层通用能力 | 代码仓库 JSON（`src/task_flow/builtin/`），启动时加载并校验 | 用户只读，可复制为"我的任务流"后编辑 |
| 用户流（user） | 用户在 UI 创建 | 数据库，用户隔离 | 可编辑 |

内置流与用户流共用同一套解析、校验、编译、索引、执行引擎，仅来源不同。首批内置流的具体场景清单另行定义，本文档只定规范。

### 1.3 术语表

| 术语 | 含义 |
|:--:|:--|
| 任务流（TaskFlow） | 一条可复用的任务执行流程定义，由若干步骤组成 |
| 步骤（Step） | 流程的基本单位：名称 + 自然语言指令 + SKILL 引用 + 执行者 + 限制条件 |
| 并行子流（Subflow） | 从主流分叉出的并行执行线，拥有自己的步骤序列 |
| 执行者（Executor） | 步骤的执行主体：主 Agent / 指定 SubAgent / Auto（运行时决定） |
| SKILL | 系统技能体系中已注册的技能 |
| MCP 服务 | 流级配置的外部工具服务，所有步骤共享 |
| 执行计划（ExecutionPlan） | 任务流 schema 的编译产物，执行器直接消费 |
| 执行记录（Execution） | 一次任务流运行的完整 trace，用于验收与回放 |
| 中途接管 | 用户已手动完成任务的一部分，指定从流程中间步骤接入执行，已有产出作为上游状态注入 |

## 二、总体架构

编译期（保存/发布时触发，纯程序逻辑、可测试、可复现，不调用 LLM）与运行期（执行任务时，LLM 介入）分离。**编译期能抓的错绝不拖到运行时**——用户在保存时就报错，而不是跑起来才失败。

```
用户保存 / 发布任务流
        │
┌───────▼───────── 编译期（确定性）────────────────┐
│ ① 结构解析器    UI 数据 → TaskFlow schema        │
│ ② 数据校验器    安全扫描 + 结构校验（清单化 Pass）│
│ ③ 流编译器      schema → 执行计划                 │
│ ④ 流程索引器    抽语义摘要 → 检索索引             │
└─────────────────────────────────────────────────┘
        │ 发布落库（schema + 执行计划 + 索引）
┌───────▼───────── 运行期（LLM 介入）──────────────┐
│ ⑤ 流程路由器    检索候选 + LLM 终选 → 选流/降级   │
│ ⑥ 执行器        逐单元执行执行计划，维护状态      │
│                （校验回退、fork-join、SubAgent）  │
└─────────────────────────────────────────────────┘
```

设计原则：

- **轻量模型**：任务流绝大多数是线性 + 少量并行分叉。v1 不引入 IR / 基本块 / DAG 等图论设施，执行计划 = 执行单元数组（step / fork）。v1 不支持条件分支——需要分支时拆成多条流，或走通用 Agent 循环。
- **代理模式**：路由器只做选路与委托，不碰执行细节；新增任务流不需要改动路由代码（开闭原则）。
- **组件唯一定义**：六个组件只在上图定义一次，后续章节只做细化、不重复定义。

## 三、数据模型

### 3.1 任务流 schema v1

```json
{
  "schema_version": "1.0",
  "id": "tf_01J8EXAMPLE",
  "name": "深度研究报告",
  "description": "给定主题，检索资料、分析对比，产出结构化研究报告",
  "source": "user",
  "status": "published",
  "trigger_examples": ["帮我调研一下 XX", "对比一下 A 和 B"],
  "mcp_services": ["web-search", "file-writer"],
  "steps": [
    {
      "id": "s1",
      "name": "需求澄清",
      "instruction": "确认研究主题边界、输出格式与篇幅要求，不开始检索",
      "skills": "auto",
      "executor": "main",
      "constraints": "只澄清，不执行检索",
      "checkpoint": false
    },
    {
      "id": "s2",
      "name": "并行检索",
      "instruction": "分头检索中英文资料",
      "skills": "auto",
      "executor": "auto",
      "checkpoint": true,
      "parallel": [
        {
          "name": "中文资料",
          "steps": [
            { "id": "s2a1", "name": "中文检索", "instruction": "...", "skills": "auto", "executor": "auto" }
          ]
        },
        {
          "name": "英文资料",
          "steps": [
            { "id": "s2b1", "name": "英文检索", "instruction": "...", "skills": "auto", "executor": "auto" }
          ]
        }
      ]
    },
    {
      "id": "s3",
      "name": "撰写报告",
      "instruction": "基于上游检索摘要撰写报告并保存到工作区",
      "skills": ["report-writing"],
      "executor": "auto",
      "checkpoint": true,
      "example": "# 调研报告\n## 结论\n...\n## 对比分析\n...\n## 引用来源"
    }
  ]
}
```

字段约定：

- `source`：`builtin` | `user`。
- `status`：`draft` | `published`，只有 published 可被路由命中。
- `skills`：`"auto"`（Agent 自行选择）或技能名数组（显式指定一个或多个）。
- `executor`：`"main"`（主 Agent）| `"subagent:<角色名>"`（指定 SubAgent）| `"auto"`（运行时决定，默认）。
- `checkpoint`：`true` 表示该步骤完成后插入校验节点（见 5.3）。
- `example`：可选，用户手动提供的参考样例（期望产出的格式 / 结构 / 风格），作为用户给出的产出规范；执行该步骤时注入上下文供 Agent 参照，也是 checkpoint 校验的对照基准（见 5.2、5.3）。
- `parallel`：可选；存在时该步骤为 fork 单元，子流配置（steps / instruction 等）与主流相互独立。

### 3.2 执行计划（编译产物）

执行器不直接消费 schema，而是消费编译后的执行计划——一个**执行单元数组**，单元只有两种类型：`step` 与 `fork`。

```json
{
  "plan_version": "1.0",
  "flow_id": "tf_01J8EXAMPLE",
  "schema_hash": "sha256:ab12...",
  "units": [
    { "seq": 1, "type": "step", "ref": "s1", "executor": "main", "checkpoint": false },
    {
      "seq": 2,
      "type": "fork",
      "ref": "s2",
      "branches": [
        { "name": "中文资料", "steps": ["s2a1"] },
        { "name": "英文资料", "steps": ["s2b1"] }
      ],
      "join": "all",
      "checkpoint": true
    },
    { "seq": 3, "type": "step", "ref": "s3", "executor": "auto", "checkpoint": true }
  ]
}
```

- `schema_hash`：执行计划与 schema 版本绑定，schema 变更后必须重新编译。
- fork 单元的 `join: "all"` 表示全部分支完成后才汇合（v1 唯一汇合策略）。

## 四、编译期管线

### 4.1 结构解析器

将 UI 提交的数据封装为 TaskFlow schema，实现前后端数据对接。输入是 JSON 而非源码，不做词法/语法分析，只保证结构可读、不判断语义，此段很轻。

### 4.2 数据校验器

拆两道 Pass，均做成独立可开关、可单测的校验项。

**安全扫描**（威胁模型：用户填写的是自然语言指令，真实注入面是**提示注入**与越权指令，而非 SQL 注入）：

| 规则 | 说明 |
|:--|:--|
| 提示注入模式 | 扫描"忽略之前的指令""你现在是..."、伪造系统消息等已知注入模式（模式库可维护） |
| 危险指令 | 明确的破坏性指令词（删除数据、格式化、关停服务等） |
| 越权诱导 | 诱导绕过权限、访问他人数据、泄露密钥等表述 |

**结构校验**：

| 规则 | 说明 |
|:--|:--|
| 步骤合法 | 步骤非空；id、名称唯一 |
| 引用存在 | `skills`、`executor`、`mcp_services` 引用的对象在系统中存在（`auto` 除外） |
| 并行合法 | 分支数量不限（至少 1 条）；每条分支至少 1 步；子流嵌套层级 ≤ 2 |
| 字段长度 | 名称 / 指令 / 示例超长时拒绝或截断（保护上下文预算，阈值可配） |
| 无环性 | 子流为内联定义、不可引用主流，天然无环；若未来支持流间引用，须显式声明循环 |

### 4.3 流编译器

schema → 执行计划：拉平步骤为执行单元数组，解析 fork 分支与汇合点，绑定 `schema_hash`。纯函数，输入相同输出必相同，可直接单测。

### 4.4 流程索引器

从 schema 抽取可检索描述（名称、描述、触发示例、步骤摘要），写入检索索引，供运行期路由匹配。**与流编译器职责分离**：前者产出可检索描述，后者产出可执行计划。

## 五、运行期：路由与执行

### 5.1 流程路由器

输入当前任务，输出三选一：**命中某条执行计划 / 走通用 Agent 循环 / 建议新建任务流**。

- 召回：embedding 相似度 + 关键词，对索引取 top-K（K=3）。
- 终选：LLM（可用低成本模型）判断候选是否适用于当前任务。
- 未命中：走通用 Agent 循环完成任务；若过程可复用，Agent 可提示用户"是否将本次执行过程保存为任务流"。
- 用户在 UI 或指令中显式指定任务流时，优先于检索结果。

### 5.2 步骤状态机

执行器逐单元执行，每个步骤实例的状态机：

```
pending → running → checking(仅 checkpoint 步骤) → done
              │           │
              └──→ retrying（≤2 次）→ degraded（主 Agent 通用兜底）→ failed（上报用户）
```

步骤执行上下文保持最小化：只注入当前步骤的指令、限制条件、示例（`example`，如有）与上游状态摘要——短指令遵循度更好，也控制上下文体积。

### 5.3 校验与回退

- `checkpoint: true` 的单元完成后插入校验节点：规则检查或轻量模型评审（如"产出是否包含要求的三个部分"）；若步骤提供了 `example`，以示例为对照基准检查产出的格式 / 结构 / 关键要素。
- 不合格 → 回退重试（最多 2 次，重试时附带校验反馈）；仍不合格 → 降级由主 Agent 通用能力兜底；兜底仍失败 → 标记 `failed` 并上报用户，不静默跳过。

### 5.4 并行执行（fork-join）

- fork 单元的**每条分支默认委派一个 SubAgent 并行执行**——这是提升子智能体委派率的核心机制；分支步骤的 `executor` 可显式覆盖。
- 并发上限 4（可配），超出排队。
- `join: all`：全部分支完成后，各分支产出**摘要**注入下一单元的上游状态（只注摘要、不灌全文，控制上下文体积）。
- 任一分支失败，按 5.3 同一策略处理；分支最终失败则整个 fork 失败。

### 5.5 中途接管（用户部分完成任务的接入）

用户已手动完成任务的一部分时，可要求 Agent 按任务流从中间任意步骤接管，而非从头执行。

- **入口指定**：①发起时显式选择入口步骤；②在对话中描述已完成内容，由路由器对齐到最合适的入口步骤——对齐结果须向用户确认后才执行。
- **上游状态重建**：用户已有产出（文本、工作区文件）作为"用户提供的上游状态"注入执行器，替代前序单元的执行结果；该部分状态在执行记录中标记来源为 `user_provided`。
- **校验**：入口步骤之前的 checkpoint 不补做；可选对注入产出做一次轻量评审，结果提示用户但不阻断（用户的产出不强制返工）。
- **后续执行**：从入口步骤起按正常语义执行，状态机、校验回退、fork-join 规则不变。

### 5.6 运行时安全（补静态扫描的漏）

工具参数白名单、SQL 只读、单步超时、总步数上限、SubAgent 内部循环检测。

**HITL 策略**：是否需要人工介入由 Agent 自动判断，任务流 schema 不暴露任何 HITL / 审批配置项；系统级强制审批场景（如项目外命令调用审批）沿用现有 HITL 审批契约照常触发，执行器不为此做特殊分支。

## 六、与现有运行时集成

- **路由入口**：位于 chat 入口——用户消息到达后、进入通用 agent 图（LangGraph）之前。
- **执行形态**：命中后，执行器作为 agent 图中的一个子图运行，与主会话共享消息历史与工作区上下文。
- **执行记录（Execution）**：每次运行生成一条记录——`execution_id`、`flow_id`、`schema_hash`、每单元的输入/输出/耗时/校验结果/重试次数、最终状态、中途接管的入口步骤与注入状态来源（`user_provided` / 步骤产出），并关联可观测平台（Langfuse / LangSmith）的 trace id。**这是用户验收"Agent 是否按流执行"的核心手段**，步骤级 trace 可回放。
- 评估指标（路由命中率、步骤一次通过率、平均重试次数）v1 先落数据，看板后续迭代。

## 七、UI 设计

### 7.1 设计红线

- 不做思维导图、树形图、节点编辑器。任务流大多是线性且步骤清晰的规划，不让用户疲于画图。
- 不向用户暴露后端系统级工具。工具由 Agent 执行时自动选择，用户只配置 SKILL、MCP、执行者。
- 不暴露 HITL / 审批类配置：是否需要人工介入由 Agent 自动判断（见 5.6）。
- 编辑原则：**枚举值用选择器**（SKILL 多选 / Auto、执行者、MCP 服务），**自由语义用自然语言**（名称、指令、限制条件）。

### 7.2 列表页

- 卡片式：缩略图（根据流结构实时渲染的简图小组件，非截图）、名称、描述摘要、来源徽标（内置 / 我的）、最近更新时间。
- 分页，默认按最近更新排序。
- 支持路由级前进 / 后退。
- 内置流只读，卡片操作为"复制为我的任务流"。

### 7.3 详情页

左简图 + 右配置：

- **左侧简图**：步骤按序自上而下排列；每步一个圆形节点，圆内数字表示第几步；颜色区分主流与子流；hover 弹出简要信息卡（标题 + 部分描述），离开消失；遇到并行子流时该步左右分叉，各子流仍自上而下排列。
- **右侧配置**：上部为流全局配置（名称、描述、触发示例、MCP 服务）；下部为选中步骤的配置（步名、指令、SKILL、执行者、限制条件、示例（可选）、是否校验点），是主要编辑区。
- MCP 为流级配置，步骤继承、不可覆盖（v1）。
- 交互：单击圆点选中步骤；右键菜单 = 新增步骤 / 在下方插入步骤 / 插入并行子流 / 编辑 / 删除。
- 保存即触发编译期校验，错误就地标注在对应步骤上。

### 7.4 与 Chat 集成

- 路由命中任务流时，消息流中插入**执行卡片**：流名称、当前步骤、进度、状态，可展开查看各步结果与 trace。
- 未命中但任务完成后，Agent 可提示"保存为任务流"，一键跳转新建页并预填步骤草稿。
- 发起任务流时支持"从第 N 步开始"，并可粘贴文本或引用工作区文件作为已有产出（中途接管，见 5.5）。

## 八、版本与存储

- **用户流**：存数据库，`user_id` 隔离。保存（draft）即运行校验；发布时重新校验并编译执行计划，plan 与 `schema_hash` 绑定。已发布流再编辑会生成新 draft，不影响在用的执行计划，重新发布才替换。
- **内置流**：`src/task_flow/builtin/*.json` 随代码仓库发布，启动时加载并跑同一套校验，校验失败启动告警（不阻断）；内置流更新随系统版本走。

## 九、开放问题

1. **执行中介入**：用户能否暂停执行、修改当前步指令、跳过某步。
2. **首批内置流清单**：场景范围另行定义，不阻塞本模块开发。
3. **条件分支**：v1 不支持，视真实使用需求再议。
4. **多租户**：v1 单部署多用户，多租户为长期演进。
