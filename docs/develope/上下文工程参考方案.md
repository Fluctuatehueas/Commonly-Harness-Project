结合你之前对 DeepSeek 光学压缩、Claude Code 分层清除、Cursor 可回溯引用、OpenAI 黑盒压缩的梳理，再叠加搜索到的 2026 年前沿研究，一个更进一步的方案轮廓是清晰的：**把“压缩时机”从固定阈值里解放出来，交给 Agent 自己判断；把“压缩对象”从笼统的对话历史拆成可独立管理的分层；把“压缩结果”从一次性摘要变成可验证、可回溯的结构化产物。**

下面是一个融合了主流工程实践与最新研究结论的方案框架。

### 核心思路：从“被动压缩”转向“元认知压缩 + 分层预算”

当前主流做法（包括你之前提到的 Claude Code 水位线、OpenAI 阈值触发）都有一个共同盲区：**压缩触发点是固定的，与任务的实际进展无关**。NeurIPS 2025 的 SelfCompact 研究直接指出了这个问题：固定间隔压缩“对轨迹结构是盲目的”，可能在推导中途或搜索尚未收敛时丢弃部分结果。他们的解法是给模型一个内联的“压缩工具”和一个轻量 rubric，让模型自己判断何时压缩（子任务已解决、轨迹正在收敛）以及何时抑制（推导中、卡住时）。实验结果显示，这种自适应压缩在数学任务上比无压缩基线提升最高 16.7 分，在 agentic 搜索上提升 5–9 分，同时单问题成本降低 30–70%。

这给你之前的评估机制提供了一个新的维度：**不应该只评估“压缩后信息丢了多少”，还应该评估“压缩时机选得对不对”**。一个在错误时机执行的完美摘要，可能比不压缩更糟。

### 方案骨架：三层预算 + 元认知触发 + 可验证产物

**第一层：预算分配从“单水位线”改为“分层配额”**

你之前的设计是单条 token 水位线。SCOPE 框架（ACL 2026）给出了一个更精细的做法：把上下文拆成**记忆、工具 schema、系统提示**三个层，用一个轻量 planner（上下文 bandit）在固定总预算下动态分配三者的配额。在 60K token/轮的条件下，SCOPE 做到了 96.8% 的决策保真度和 4.46 倍压缩，任务成功率与全上下文只差 0.9%，但只用了 22% 的 token。

对你的启示是：**工具结果、对话记忆、系统指令不应该抢同一个水位线**。工具结果可以激进压缩（甚至直接转文件引用，像 Cursor 那样），系统指令几乎不压，对话记忆的压缩预算根据任务阶段浮动。这比单一水位线更接近“该压的压、不该动的不动”。

**第二层：触发机制引入“轨迹信号”而非纯 token 计数**

SelfCompact 的 rubric 给出了几个可操作的信号：子任务已解决、轨迹正在收敛、推导中途、卡住。你可以把这些信号作为**触发前的前置判断**，而不是让水位线独自决定。例如：水位线到了 70%，但 Agent 正处于一个工具调用的关键链中（刚发出一个搜索、还没拿到结果），此时应该**延迟压缩**，等这个子任务收敛后再执行。评估时可以把“压缩延迟量”和“延迟后的任务成功率”作为一对指标来调参。

另一个可借鉴的触发思路来自 Cat（ACL 2026 Findings）：把上下文管理本身做成一个**可调用的工具**，Agent 在觉得“当前上下文开始变脏/变长”时主动调用它来压缩历史轨迹。这比被动水位线更灵活，但需要 Agent 本身具备这种元认知能力（或者通过训练获得，他们的 SWE-Compressor 在 SWE-Bench-Verified 上达到 57.6% solved rate）。

**第三层：压缩产物从“一段摘要”升级为“结构化 + 可验证 + 可回溯”**

你之前已经考虑了 Cursor 的“历史文件引用”和 Claude Code 的焦点压缩。这里可以再叠一层：**给每次压缩产出一个轻量的“压缩回执”**。IETF 有一份草案提出了 Ephemeral Context Compaction Receipt 的概念：每次有损压缩时，记录源条目的 Merkle root、压缩输出的哈希、继承的敏感度上限、保留期限等，并且用签名保证不可抵赖。对于你的场景，不需要做到密码学级别，但**记录“压了什么、依据什么规则、保留了哪些锁定片段、原始内容的定位符”** 是一个很实用的工程习惯。

结合你之前提到的“锁定片段校验”，一个完整的压缩单元可以长这样：

1.  **压缩前**：标记锁定片段（文件路径、错误码、关键决策理由）。
2.  **压缩执行**：按分层配额选择压缩器（工具结果→文件引用/尾部截断；旧对话→结构化摘要；系统指令→不压）。
3.  **压缩产物**：结构化摘要 + 原始内容的引用/定位符（如 Cursor 的历史文件路径）+ 锁定片段的存在性校验结果。
4.  **评估探针**：除了你之前设计的召回问题，**额外加一个“压缩时机合理性”的 LLM 裁判**：让裁判看压缩前后的轨迹片段，判断“如果此时不压缩，后续几步是否会出现信息缺失；如果压缩了，是否丢失了正在进行中的中间结果”。

### 评估机制需要新增的两个维度

你原来的评估维度（压缩效率、事实召回、决策连续性、目标适应性）已经比较完整。结合上面的方案，建议补两个：

**维度一：压缩时机质量（Compaction Timing Quality）**
对每一次压缩事件，记录触发时的轨迹状态（子任务是否收敛、是否有未返回的工具调用）。用 LLM 裁判结合规则判断：这个时机是否合适？如果时机被标记为“过早”，即使压缩后的信息保留得很好，这次压缩也应该计入负面统计。SelfCompact 的实验已经证明，时机对了，同样的压缩策略可以带来显著的净收益。

**维度二：压缩产物的“可回溯成本”**
如果一个压缩产物附带了指向原始内容的引用，评估时应该测量：Agent 在需要找回细节时，**实际花了多少 token 和步数去检索原始内容**。Cursor 的引用方案降低了压缩频率，但如果每次找回都要多花 3 步，这个成本也需要计入。这个指标可以帮你决定：引用应该多细（文件路径 vs. 行号范围 vs. 全文快照）。

### 与现有主流做法的对比定位

| 维度 | Claude Code | Cursor | OpenAI compact | **你的融合方案** |
|---|---|---|---|---|
| 触发 | 水位线 + 手动焦点 | 动态发现 + 引用兜底 | 服务端阈值 | **水位线 + 轨迹信号 + Agent 主动调用** |
| 对象 | 工具结果优先 | 工具输出转文件 | 不透明全局 | **分层配额（记忆/工具/指令分开管理）** |
| 产物 | 焦点摘要 | 摘要 + 历史引用 | 加密块 | **结构化摘要 + 引用 + 锁定片段校验 + 轻量回执** |
| 评估 | 功能可用性 | 缓存命中/成本 | 压缩率 | **原有维度 + 时机质量 + 回溯成本** |

这个方案的“新”不在于发明了某个单点技术，而在于把 2026 年分散出现的几个研究结论（自适应时机、分层预算、可调用压缩工具）与已有的工程实践（焦点摘要、文件引用、锁定片段）拼成了一个**可观测、可评估、时机感知**的闭环。最需要你根据自己场景调参的两个自由度是：**轨迹信号的阈值**（什么算“收敛”、什么算“卡住”）和**分层配额的初始比例**。建议先用一个中等长度的 Agent 任务集跑基线，记录每个压缩事件的时机标签和后续成功率，再逐步收紧触发条件。
