## 一、上下文压缩质量评估
在 Agent 项目里评估上下文压缩，不是看“压得多不多”，而是看压缩后还能不能稳定支撑任务完成。真正有用的评估标准通常只有三类：信息保真度、任务成功率、综合成本收益。只要压缩以后关键事实没有丢、推理链没有被破坏、整体时延和费用确实下降，这个上下文压缩方案才算有效；反过来，哪怕压缩率很高，只要导致答非所问、遗漏约束或动作失真，就不能算合格。  


在 Agent 项目里，真正需要评估的不是“压缩质量”这个抽象概念，而是压缩对任务系统造成的具体影响。可以把它拆成四个层面：  
|评估层面|	核心问题|	重点观察项|	常见失真方式|
|--|--|--|--|
|信息层|	关键内容是否被保留|	事实、约束、目标、状态、依赖关系|	漏掉前提、改写原意、时间顺序错乱|
|推理层|	后续决策是否还能成立|	计划质量、工具调用依据、步骤连贯性|	摘要正确但推理链断裂|
|任务层|	最终任务是否完成|	成功率、准确率、返工率、人工接管率|	能回答问题但做不成任务|
|资源层|	成本是否真的下降|	token 消耗、响应时延、计算轮次|	压缩省 token，却增加重试成本|

评估的第一步不是选指标，而是**先界定你的 Agent 属于哪一类**。如果是问答型 Agent，信息保真和回答正确更重要；如果是工作流执行型 Agent，约束保留、状态一致、动作可追踪更关键；如果是多轮协作型 Agent，长期记忆压缩后的冲突率、遗忘率、重复确认率会比单轮准确率更值得关注。  

### 1. 区分有几种上下文
- 交互上下文：System Prompt, 用户偏好、记忆、**已确认的结论**等
- 任务上下文：任务状态、任务目标、任务依赖关系、输入材料、、约束条件、预期输出等
- 运行上下文：中间状态、工具返回、错误记录、计划草案、执行轨迹、人工介入信息等


### 2. 评估上下文压缩质量，看这5个维度
真正能指导优化的评估框架，通常离不开 5 个维度：保真、可用、稳定、成本、边界。它们不是并列打分项，而是一套判断顺序。先看能不能用，再看值不值得用，最后看在哪些场景不能用。

- 保真度：关键事实有没有丢
- 可用性：压缩后还能不能完成任务
- 稳定性：不同轮次、不同输入下是否表现一致
    - 压缩结果是否一致
    - 长任务是否更容易退化
    - 异常输入是否触发灾难性错误
- 成本收益：省下来token的值不值得
    - 上下文压缩往往是为了控制 token、降低时延、提升吞吐，但评估时不能只看直接节省。因为有些压缩方案会带来隐藏成本：重试增加、澄清轮次变多、人工接管上升、故障排查复杂度变高。最后账算下来，表面省了模型成本，整体交付成本反而更高。
    - 
- 边界条件：在哪些场景下不能压，或不能这样压
    - 例如下面几种情况，通常就不适合强压缩：
        - 任务包含多个互相制约的硬约束
        - 工具执行具有不可逆后果
        - 长流程中间状态高度依赖前文细节
        - 用户多次修订需求，且修订彼此冲突
    - 一旦识别出这些边界，评估就不再是“统一打分”，而是要形成路由策略：哪些任务可以摘要压缩，哪些任务只能结构化提炼，哪些任务必须保留原始片段并附带引用定位。只有做到这一层，评估结果才真正能反过来指导系统设计。
