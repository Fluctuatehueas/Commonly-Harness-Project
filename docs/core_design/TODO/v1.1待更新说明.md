## 一、插件市场（参考DeepSeekHarness的插件模块进行制作）

> 调研结论：DSH（DeepSeek Harness）基于 Cordis 内核，内核位于 Harness 之下，一切能力皆插件、可替换；插件是 npm 包，分 host 半与 client 半，市场只负责目录、安装、更新、启停、卸载，真正的动作交给宿主 `pluginManager`。
>
> 本项目不采用「内核反转」。插件与系统底层平级，定位是外设：Agent 是 CPU，Harness 是主板，Plugin Bus 是外设总线。插件通过统一协议接入，语言不限（Python / JS / C# / Java 等），用于补能力、接业务、扩界面；插件崩溃或卸载只掉一个外设，不影响主板。
>
> 代价对比：不用重写 `main_agent` 组合根，也不需要 Python 热卸载；新增的是 Plugin Protocol、外设总线、多语言 SDK 与子进程管理。内核只做握手、权限、生命周期和路由，不接管系统内部能力。

### 1.1 需要准备插件的API接口，这个是底层基础设置

插件 API 分两层：Plugin Protocol（插件 ↔ 总线，语言无关）与管理侧 HTTP API（前端、命令系统、Agent 用）。

**Plugin Bus（外设总线）** `src/plugin_bus/`

- `manifest.py`：解析、校验 manifest，做 `protocolVersion`、`harnessVersion`、权限与能力声明检查
- `protocol.py`：JSON-RPC 2.0 信封、方法名、错误码、超时与重试约定
- `transport/stdio.py`：本地插件，一行一条 JSON，由总线拉起子进程
- `transport/http.py`：远程插件，POST + SSE 可选，支持已有服务直接接入
- `registry.py`：能力注册表，把 `plugin.describe` 的结果注入工具清单、资源目录与提示词
- `lifecycle.py`：installed → verified → enabled → running → unhealthy → disabled → uninstalled
- `permissions.py`：按 manifest 声明在总线侧拦截，未声明即拒绝
- `health.py`：心跳、启动探活、崩溃退避重启、空闲回收
- `sandbox_verify.py`：装前在 OpenSandbox 内跑协议冒烟与行为采集
- `adapters/inprocess.py`：内置插件的进程内适配器，与外部插件共用同一份 manifest 与协议语义

**Plugin Protocol（JSON-RPC 2.0）**

- 总线 → 插件：`plugin.initialize`、`plugin.describe`、`plugin.health`、`plugin.shutdown`、`tool.call`、`resource.list`、`resource.read`、`prompt.get`、`hook.invoke`、`event.notify`
- 插件 → 总线：只开放声明过的 `host.storage.*`、`host.secret.get`、`host.log`、`host.progress`；宿主内部对象不直接暴露
- 本地插件走 stdio，远程插件走 HTTP；两种传输共用同一套方法与错误码
- `protocolVersion` 主版本不匹配直接拒绝握手，不做兼容猜测
- 所有调用带超时；hook 超时或异常只降级并记轨迹，不阻断主流程

**能力（v1.1 六类全做）**

| 能力 | 内容 | Agent 侧如何看到 |
| :-- | :-- | :-- |
| `tool` | 带 JSON Schema 的工具 | 注入工具清单，可直接调用 |
| `resource` | 可列举/读取的外部资源（文件、表、业务对象） | 注入资源目录，配合 `resource.read` |
| `prompt` | 领域提示词 / 技能片段 | 按触发条件注入系统提示 |
| `hook` | before/after model、wrap tool 等拦截点 | 总线回调，失败降级 |
| `ui` | 声明式 slot + 沙箱 iframe 页面 | 控制台渲染，不注入主前端 bundle |
| `integration` | 外部系统连接器（认证、API、权限） | 与 tool/resource 组合，凭据走配置与权限 |

**SDK**

- 官方维护 Python 与 TypeScript 两个 SDK，覆盖市场首批插件
- C# / Java 先提供协议文档与最小样例，按协议接入；协议本身语言无关，不绑定框架
- SDK 只封装握手、能力注册、心跳、错误与重试，不替插件做业务

**管理侧 API**

| 接口 | 说明 |
| :-- | :-- |
| `GET /plugins/market/catalog` | 市场目录，支持关键词、分类、能力类型、分页 |
| `GET /plugins/market/{plugin_id}` | 插件详情、能力、权限、版本历史 |
| `GET /plugins` | 当前用户已安装插件（含内置与远程） |
| `POST /plugins/install` | 安装本地包或注册远程服务，返回异步 job |
| `POST /plugins/{id}/toggle` | 启用 / 停用（拉起或停止外设） |
| `POST /plugins/{id}/restart` | 重启插件进程 / 重连远程服务 |
| `GET /plugins/{id}/capabilities` | 插件当前上报的能力清单 |
| `GET /plugins/{id}/health` | 健康状态、延迟、最近错误 |
| `DELETE /plugins/{id}` | 卸载（市场自身拒绝卸载） |
| `GET /plugins/updates` | 可更新列表 |
| `POST /plugins/{id}/update` | 更新到指定版本 |
| `GET /plugins/jobs/{job_id}` | 安装/更新/验证进度 |

- 安装、启停、更新全部只走 Plugin Bus，市场不直接改磁盘、不自己起进程。
- 安装是异步任务，复用技能安装那套 job + 底部进度卡，前端不再做第二套进度模型。
- 所有接口按当前用户过滤：列表、启停、卸载、审计只作用于 `user_id` 自己的数据；内置插件对所有用户可见，启停状态各自独立。

### 1.2 对插件定义数据结构，用于UI演示和调用

`manifest.json` 是插件对外的唯一描述，市场展示、安装校验、握手与能力注入都读它。

```json
{
  "plugin_id": "context-compactor",
  "name": "上下文压缩器",
  "version": "1.0.0",
  "protocolVersion": "1.0",
  "description": "按会话类型裁剪历史，降低长对话 token 消耗。",
  "author": { "name": "GuiQIHueas", "homepage": "" },
  "license": "MIT",
  "tag": ["上下文压缩和管理", "插件"],
  "capabilities": ["tool", "resource", "prompt", "hook", "ui"],
  "runtime": {
    "kind": "subprocess",
    "language": "python",
    "command": "python",
    "args": ["-m", "context_compactor"]
  },
  "transport": { "kind": "stdio" },
  "permissions": ["context:read", "storage:write", "ui"],
  "env": { "python": ">=3.11" },
  "ui": {
    "slots": [
      { "slot": "chat.sidebar", "title": "上下文占用", "entry": "ui/index.html" }
    ]
  },
  "harnessVersion": { "min": "1.1.0", "max": "1.x" },
  "like": 100,
  "downloadCount": 100,
  "dist": { "url": "", "sha256": "", "size": 0 },
  "changelog": []
}
```

远程插件只换运行段：`"runtime": { "kind": "remote" }`，`"transport": { "kind": "http", "url": "https://..." }`。

- UI 展示字段和后端校验字段共用同一份 manifest，市场卡片不额外造一套结构。
- `permissions` 必须显式声明，未声明的权限总线侧直接拒绝，不做隐式放行。
- `capabilities` 声明插件对外提供什么；`plugin.describe` 的上报必须与声明一致，不一致握手失败。
- `env` 只说明运行环境要求，不代替依赖安装；依赖由插件包自带或在沙箱内准备。
- `configSchema`（可选）描述插件配置表单，前端通用渲染；密钥走用户级密钥存储，不写进 manifest。
- 详情页复用 MCP 服务列表那套悬停详情组件（见第 2.4 节 UI 渲染），不重复开发。

### 1.3 插件内容存储形式

磁盘是插件内容与版本的权威源，数据库只存安装记录、启停状态、配置与审计。

```text
src/agent/plugins/builtin/              # 系统默认插件，随版本发布，只读
  {plugin_id}/{version}/

USER_DATA_DIR/users/{user_id}/plugins/  # 用户插件，按用户隔离
  {plugin_id}/
    current.json          # {"version": "1.0.0"}
    versions/1.0.0/       # 插件包（本地子进程插件）
    versions/1.1.0/       # 版本共存，回滚只改 current.json
    data/                 # 插件私有数据，跨版本保留，跨用户不可见
  plugins-disabled/{plugin_id}/{version}/
  .cache/catalog.json     # 市场目录缓存，按用户
```

- 三级来源：系统内置（全用户共享、只读）、用户安装（按 `user_id` 隔离）、项目级（跟项目走）。加载顺序为 项目级 > 用户级 > 系统内置。
- 远程插件没有包目录，只记录 `endpoint + protocolVersion + 配置`；卸载只删登记，不碰对方的服务。
- 用户不允许安装与系统内置同 `plugin_id` 的插件，防止影子覆盖；内置插件可按用户停用，但不能卸载。
- PostgreSQL 表：`plugin_install`（user_id、plugin_id、version、source、sha256、status、installed_at）、`plugin_user_state`（user_id、plugin_id、enabled，内置插件同样落这张表）、`plugin_config`（user_id、plugin_id、config_json、secret_ref）、`plugin_audit`（user_id、操作、plugin_id、版本、结果、时间）。不建插件内容表，避免磁盘与数据库两份事实源。
- 用户隔离边界：插件列表、启停状态、私有 data、配置与密钥、进程实例、审计全部按 `user_id` 分区；A 用户安装或停用不影响 B 用户；卸载只动当前用户目录与进程。
- 插件进程按 `(user_id, plugin_id, version)` 复用，空闲超时回收，下次调用自动拉起；不同用户不共享进程与内存。
- 项目级插件放 `.commonharness/plugins/{plugin_id}/`，只在对应项目的会话里被发现，不在控制台插件管理页展示（与 2.5 保持一致）。
- 按项目硬约束，`.commonharness` 目录内的代码不允许在宿主直接执行，项目级插件只在沙箱内拉起。
- 插件自身依赖不自动安装到宿主：依赖必须随包携带，或声明为沙箱依赖，避免安装环节变成任意代码执行入口。

### 1.4 插件制作归属

按归属分五类，信任等级依次降低：

| 归属 | 来源 | 运行位置 | 说明 |
| :-- | :-- | :-- | :-- |
| 官方内置 | 随版本发布 | 宿主进程内适配器 | 所有用户默认拥有，可停用不可卸载 |
| 集成方私有 | 甲方私有市场 | 按甲方部署策略 | 业务系统连接器，走白名单与私有目录 |
| 社区 | 自建 catalog | 用户宿主侧子进程（验证后） | 需哈希/签名校验 + 沙箱试运行 |
| 用户本地 | URL / 目录导入 | 用户宿主侧子进程（验证后） | `/plugin get <url>` 走同一套安全闸门 |
| Agent 自迭代 | Agent 生成 | 先沙箱，后按上两档 | 验证通过后仍需用户确认 |

- manifest 必须写清 `author` 与来源，市场列表展示来源，不允许匿名发布。
- 用户自制插件默认只归属当前用户，不自动进公共目录；要发布走市场提交流程。
- 集成模式可关闭公共市场，只允许私有目录与白名单插件。

### 1.5 插件市场管理（如果可以，可以获取Deepseek的插件市场进行安装和集成）

- 入口放控制台「插件」导航，面板三页签：发现 / 已安装 / 可更新（带计数角标），交互心智对齐「外设管理器」。
- 发现页：分类 chips、搜索、排序（热门 / 最新 / 名称）、按能力类型和来源筛选；卡片可展开详情，安装后状态就地更新，不整页刷新。
- 详情页：说明、能力清单、权限清单、`protocolVersion`、运行形态（本地 / 远程）、语言、仓库地址、版本历史、健康状态。业务集成类插件要单独展示会获得哪些外部系统权限。
- 已安装页：启停、重启、卸载、版本、来源、权限；系统内置插件标记「系统」，只保留停用开关；用户之间的列表互不可见。
- 可更新页：逐条「更新到 x.y.z」+ 一键顺序更新，失败不连坐，结束给一条汇总回执。
- 目录数据：自建 `catalog.json`（可分片，每片带 sha256），优先自建源，内存缓存 10 分钟；请求失败回退缓存并标记 `stale`，不把空目录当好数据覆盖。
- 私有市场：集成模式下允许配置甲方私有目录 URL（`PLUGIN_REGISTRY_URL`），与公共目录并存或替代，白名单之外一律不展示。
- DSH 导入：只读适配器对接 `awesome-dsh-plugin` 社区目录（npm 镜像优先、官方源兜底），字段映射到我们的 manifest。DSH 的 Cordis 插件不能直接运行，只做「转译导入」：能提取 SKILL 内容的按技能导入，其余条目标记「本系统不支持」，不伪装成可安装。
- 写操作只接受同源 POST，请求体有大小上限，目录只读、不带凭据。

### 1.6 插件版本管理与更新

- 两条版本轴：`protocolVersion` 管协议兼容，插件 `version` 管功能迭代；宿主只接受同主版本的协议，不兼容在详情阶段就拒绝。
- 版本目录共存 + `current.json` 原子切换；更新流程为 停旧进程 → 起新版本 → 健康检查 → 切指针，失败自动回滚并重启旧版本。
- 插件是外设进程，更新可以真正热替换，不需要重启 Harness；这是外设模型比进程内插件多出来的一项收益。
- 内置插件跑在宿主进程内，升级仍需后端重启后生效；UI 扩展刷新页面即生效。
- 崩溃策略：按退避重启，连续失败 N 次标记 `unhealthy` 并自动停用，Agent 侧看到的是「插件不可用」而不是整轮对话失败。
- 市场本体也走同一套自更新通道：路径校验 + sha256 + 产物自校验，装完如实提示是否需要重启。
- 清理旧版本时保留最近两个，避免用户刚回滚又没得回滚。
- 系统内置插件的版本跟随主程序发布，不参与用户的更新与回滚；用户只控制启停。

### 1.7 安全问题

四道闸门：声明权限 → 静态扫描 → 沙箱试运行 → 用户确认。

- 信任分级决定运行位置：内置插件进程内（源码随版本审查）；社区/用户插件默认宿主侧子进程，装前必须过沙箱；项目级插件只能在沙箱内跑；远程插件按 URL 来源与签名判定。
- 权限：manifest 显式声明（`fs:read/write`、`net`、`process`、`context:read`、`storage`、`secret`、`ui`），总线侧按声明拦截；不继承宿主环境变量，尤其不把 `DEEPSEEK_API_KEY`、数据库密码透给插件。
- 静态扫描：包结构、路径穿越、符号链接、文件数与体积上限（沿用技能包 32 MB 口径）；解释型语言扫危险调用，编译型产物校验哈希/签名，不再简单「见到可执行文件就拒绝」。
- 沙箱试运行：在 OpenSandbox 内按协议完成 `initialize → describe → smoke`，采集网络、文件、子进程行为，超时、崩溃或越权直接判失败。
- UI 隔离：插件页面只跑在 sandbox iframe 里，CSP 限制外部加载，与宿主只通过 postMessage 白名单通信，不允许直接操作主前端 DOM。
- 业务集成：外部系统凭据存用户级密钥库，按插件授权读取；安装时逐条展示会获得的外部权限，卸载时同步撤销。
- 供应链：只允许安装目录内插件（`/plugin get <url>` 例外，但同样过四道闸门）、`dist.sha256` 必填、市场拒绝卸载自己。
- 审计：安装、启停、重启、卸载、验证结果、权限与配置变更全部进 `plugin_audit`，控制台可查。
- 如实说明边界：宿主侧子进程是同等权限的独立进程，v1.1 靠「装前沙箱验证 + 运行时声明权限」收口，不是 OS 级隔离；高风险插件应只以沙箱模式运行，这条要写在详情页里。

### 1.8 Agent自我迭代插件

- 能力前提：内置一个 `plugin-development` SKILL，给 Agent 协议文档、Python/TS 模板、冒烟测试脚手架与打包脚本。
- 自己快速开发：Agent 在沙箱内生成插件包、补齐 manifest、跑 `initialize → describe → smoke`，产出可安装包，不直接装进宿主。
- 自己找插件：Agent 调市场 API 检索 → 下载到沙箱 → 静态扫描 → 按协议试运行 → 生成安全报告（提供什么能力、要什么权限、有没有越权行为）。
- 装不装由用户定：Agent 只能通过快捷选项或 HITL 卡片提议，用户确认后才走正常安装通道，且只装到当前用户名下；用户可配置是否允许 Agent 自动提议、是否允许直接本地安装。
- 业务身份也要用户点头：涉及外部系统权限的集成插件，等同于让 Agent 加入某个「组织」，授权清单要逐条确认，不能由 Agent 代为同意。
- 迭代闭环：插件使用效果进轨迹与经验库，效果不好时 Agent 提改进方案，产出新版本再走一遍验证。


## 二、新增一些能力

### 2.1 Agent对隐私保护的能力
功能描述：
Agent应对用户的隐私负责：如果遇到了会写路个人信息：如真实的身份证号、电子账户密码、银行卡密码、API_KEY、住址等个人敏感信息时，应给予风险提示。

- 风险提示在该轮对话输出完毕后，在下方给予提示。AI在分析的时候，会根据黑名单检索到敏感信息，检索到就会给这次会话标记为有风险的。告诉用户，注意风险防范。为了避免AI把敏感信息不小心暴露出去。


### 2.2 每轮对话后新增快捷选项
功能描述：
每轮对话结束后，要求Agent提供一些可以方便用户操作的快捷选项。
这些选项一般用于：
- 接着对话内容追问
- 继续完成任务开发
- 按照既定的要求进行下一步
- 依据上下文场景，帮助用户发散思维，寻找更多解决方案。

快捷选项设计
- 文本简短，尽量不超30~50个字符，一般为一句话
- 点击选项卡可直接发送消息，也可以在选项卡右侧，提供一个加入到聊天框的图标按钮。
- 选项数量2~4个即可


### 2.3 新增图像处理功能

功能描述：让Agent拥有图像处理的功能，来对图像进行科学分析、信息提取、图像识别等操作。  
- 给Agent的沙箱开明包内，提供图像处理相关环境，如Opencv，Yolo等
- 提供专门的子智能体（yaml声明式），拥有专业的图像处理能力

### 2.5 本地项目组对Agent的全局约束目录：.commonharness的机制完善

在这里，可以指定用户编写项目级别的约束、项目级别的偏好、项目版本管理文档、项目独有的技能和项目独有的插件部分。属于开发者在项目中可以自定义的内容

1. 项目级的约束：  
- 说明：是Agent在该项目内完成任务时的全局约束信息，建议只写不做什么，不建议写让Agent做什么。分条编写，简洁为主。
- 目录格式： .commonharness/limits/
- 文件格式： *.md ,*.txt 为支持的文件格式
- 支持文件个数：<=10个
- 创建项目时默认创建该目录：是
- 是否提供示例文件：是
- 优先级：高。作为Agents.md的补充组件。Agent每轮对话都必须读取该目录下的所有文件。但不是读取全部文本，而是读取文件头的摘要内容，让Agent将摘要作为一个表条目先管理起来文本，本轮对话中如果进行到某些任务符合约束表的条目，再去进行全文档的索引读取，读取完毕后，该约束条目就会被添加到Agent的上下文。




2. 项目级别的偏好：
- 说明：是Agent在该项目内完成任务时的全局偏好信息，建议写一些项目的经验偏好、如文档编写用什么字体、代码注释结构要怎么写、喜欢Agent怎样的输出等。这里不建议编写开发文档、也不建议写设计文档。这个目录最大的作用是对项目开发的版本审计与管理，是对版本开发完毕的最终总结类内容。
- 目录格式： .commonharness/preferences/
- 文件格式： *.md ,*.txt 为支持的文件格式。
- 支持文件个数：1
- 创建项目时默认创建该目录：是
- 是否提供示例文件：否
- 优先级：与用户偏好等级一致，都作为用户的偏好。


3. 项目版本管理文档：
- 说明：是用户和Agent可共同管理的项目版本文档目录。当用户需要进行多版本开发与验收时，可以在该目录下编写版本文档。
- 目录格式： .commonharness/version/
- 文件格式： *.md ,*.txt 为支持的文件格式
- 支持文件个数：不限
- 创建项目时默认创建该目录：是
- 是否提供示例文件：否
- 优先级：低，仅作为用户的参考，方便用户管理项目版本。但该目录的内容，应让AI在每轮对话后，用过快捷选项提示用户，是否需要更新当前版本文档内容？如果需要更新，则会询问：你当前在做那一版？

这个目录不会进入上下文。知识方便了用户对项目版本相关文档的管理。
文档格式：
```md

- Abstract:  -是Agent判断当前任务适合更新哪一个版本文档的条目必读条目，依次来判断并在快捷选项内告知用户需要我帮你更新v*.*.*文档吗？
- Time: yyyy/MM/dd hh:mm  
- Author:   
- Contributors:  

---

## 版本内容


```


版本内容支持用户自己设置格式，一般需要包含：当前版本的更新内容、新增功能、修复问题等。

4. 项目级别的Skill：
- 说明：是Agent在该项目内完成任务时的全局技能信息，建议写一些项目独有的技能、如图像处理、自然语言处理等。

- 文件格式： 系统支持的SKILL读取结构
- 支持文件个数：不限
- 创建项目时默认创建该目录：是
- 是否提供示例文件：否
- 优先级：是Agent的SKILL能力的额外拓扑，与系统Agent是同级别的，可以在命令系统内被发现，但无法在控制台的技能管理页面被显示。换句话说，只有当在本地项目或者集成的项目时，命令系统才可以检索到项目级别的SKILL。而控制台的全局技能管理页，只支持全局的SKILL。

## 四、发布后，相关存储结构整理和优化

由于需要分用户进行数据和资源隔离以及管理。以便用于大型服务器内。因此，这些模块的存储位置需要进行明确。

> 现状问题：源码模式把 MCP 和技能写到项目目录（`mcp/`、`.mcp/`、`src/agent/skills/`），打包模式又写到用户数据目录；而且没有一个统一的定位基准——`PROJECT_ROOT` 从代码位置推导，`USER_DATA_DIR` 指向 AppData / `~/.harness`，exe 所在目录完全没参与定位。
>
> 目标：MCP / SKILL / Plugin 的文件索引统一挂到一个基准目录 `PUBLISH_PROGRAM_PATH` 下，各模块只存相对路径。该变量指向发布后的 exe 所在目录（源码运行时为仓库根），目录不可写时整体回退到 `USER_DATA_DIR`，布局不变。
>
> 先回答：之前没有 `PUBLISH_PROGRAM_PATH`，只有 `PROJECT_ROOT`（`config.py` 第 26 行）和 `USER_DATA_DIR`。v1.1 已新增该变量与 `HARNESS_HOME`，实现细节见 `docs/core_design/v1.1/存储结构重构开发文档.md`。

**基准目录**

| 场景 | `PUBLISH_PROGRAM_PATH` |
| :-- | :-- |
| 显式设置 | 环境变量原值 |
| 未设置 | 不启用部署布局，`HARNESS_HOME = USER_DATA_DIR` |
| 建议打包 | 部署脚本显式设置为 exe 所在目录 |
| 源码调试 | 可显式设置到仓库根或 `.harness` |

`HARNESS_HOME` = `PUBLISH_PROGRAM_PATH` 可写时取它本身，不可写（Program Files / 只读挂载）或未设置时回退 `USER_DATA_DIR`。所有模块目录都从 `HARNESS_HOME` 相对推导；`HARNESS_MCP_ROOT`、`HARNESS_SKILLS_ROOT` 保留为显式覆盖。

**总布局**

```text
<HARNESS_HOME>/                       # = PUBLISH_PROGRAM_PATH，不可写时回退 USER_DATA_DIR
  mcp/
    servers.template.json             # 只读模板
    users/{user_id}/servers.json
    users/{user_id}/runtime/{server_id}/npm-cache/
    users/{user_id}/runtime/{server_id}/logs/stdio.log
  skills/
    builtin/{skill}/                  # 只读
    users/{user_id}/main/{skill}/
    users/{user_id}/subagents/{agent}/{skill}/
    users/{user_id}/skills-disabled/
    users/{user_id}/skills-state.json
  plugins/
    builtin/{plugin_id}/{version}/    # 只读
    catalog/catalog.json
    users/{user_id}/{plugin_id}/current.json
    users/{user_id}/{plugin_id}/versions/{version}/
    users/{user_id}/{plugin_id}/data/
    users/{user_id}/{plugin_id}/logs/
    users/{user_id}/plugins-disabled/{plugin_id}/{version}/
  rag/providers.template.json
  cache/
    index/{mcp,skills,plugins}.json   # 可删，重建
    catalog/
  logs/
```

| 目录 | 归属 | 可写 | 备份 | 清理 |
| :-- | :-- | :-- | :-- | :-- |
| `mcp/servers.template.json`、`skills/builtin/`、`plugins/builtin/`、`plugins/catalog/` | 发布级 | 否 | 随版本 | 不清理 |
| `*/users/{user_id}/` | 用户级 | 是 | 需要 | 按用户配额 |
| `mcp/users/{user_id}/runtime/` | 用户级运行态 | 是 | 不需要 | 空闲 / 超配额 LRU |
| `plugins/users/{user_id}/*/versions/` | 用户级 | 是 | 保留最近两个 | 旧版本 |
| `cache/`、`logs/` | 部署级 | 是 | 不需要 | 定时 |

两条规则：

- 发布级目录永远不写：用户首次使用时复制模板或建立版本标记，不反向修改共享文件。
- 路径只从 `HARNESS_HOME` 推导；`HARNESS_MCP_ROOT`、`HARNESS_MCP_WORKSPACE_ROOT`、`HARNESS_SKILLS_ROOT` 降级为调试覆盖，不再作为默认。

**文件索引（不落库）**

- MCP：`servers.json` 本身就是索引（服务 ID、传输方式、开关、工具白名单），运行态另存；不建 PG 表。
- SKILL：启动或首次访问时扫描 `skills/users/{uid}` + `skills/builtin`，只读 `metadata.json` / `SKILL.md` frontmatter，**不读全文**。
- Plugin：已安装索引来自 `current.json` + 各版本 `manifest.json`；市场索引来自 `plugins/catalog/catalog.json`。
- 索引字段统一：`id`、`name`、`version`、`path`、`mtime`、`size`、元信息摘要；正文不进索引。
- `cache/index/*.json` 只是快照缓存，可随时删除重建；变化靠 `mtime + size` 判断，安装/卸载/启停后主动失效，不引入常驻文件监听。
- 大目录分页读取，列表接口按需返回；索引构建失败直接回退实时扫描，不阻断对话。

**磁盘与 PostgreSQL 的分工**

| 模块 | 磁盘权威源 | PostgreSQL 落点 |
| :-- | :-- | :-- |
| SKILL | `skills/users/{uid}/`、`skills-disabled` | 无专属表；只有任务流 schema、轨迹事件引用技能名（档案里的 `skill_scopes` 目前只是读取占位，未落库） |
| MCP | `mcp/users/{uid}/servers.json` + `runtime/` | 无专属表；只有档案 `mcp_server_ids`、任务流 schema、轨迹事件这类引用 |
| Plugin | `plugins/builtin/`、`plugins/users/{uid}/` | `plugin_install`、`plugin_user_state`、`plugin_config`、`plugin_audit` |

- 现有代码里 SKILL 和 MCP 都是「磁盘为唯一事实源」，内容、配置、启停状态都不进 PG；PG 里只出现引用 ID。
- 引用只存 ID：档案（目前仅 MCP）、任务流、轨迹里只记 `server_id` / `plugin_id` / 技能名，不复制内容，也不存连接串和密钥。
- 敏感值统一进用户级密钥库（建议 PG `user_secret`，按 `user_id` 行级隔离）；MCP 的 `servers.json` 与插件 manifest 只留 `${SECRET:...}` 引用。
- 演进与经验库里出现 `layer=skill`、`skill_generation` 只是标注经验来自技能层，不承载技能本体。

### 4.1 MCP

**现状**

- 用户配置：`users/{user_id}/mcp/servers.json`，首次访问从部署模板复制。
- 运行态：`.mcp/users/{user_id}/{server_id}/npm-cache` 与 `logs/stdio.log`，源码模式落在项目根 `.mcp/`。
- 模板：源码模式 `mcp/servers.json`，打包模式 `USER_DATA_DIR/mcp/servers.json`。

**目标**

```text
<HARNESS_HOME>/mcp/servers.template.json
<HARNESS_HOME>/mcp/users/{user_id}/servers.json
<HARNESS_HOME>/mcp/users/{user_id}/runtime/{server_id}/npm-cache/
<HARNESS_HOME>/mcp/users/{user_id}/runtime/{server_id}/logs/stdio.log
```

- 模板与用户配置分离：模板只读，用户首次访问复制；模板升级只做字段合并提示，不覆盖用户改过的条目。
- 运行态下沉到用户目录：npm 缓存、stdio 日志、子进程工作目录都跟 `(user_id, server_id)` 走，不再共用项目根 `.mcp/`。
- 敏感信息不落 `servers.json`：现在 `headers.Authorization` 是明文，发布前改成 `${SECRET:mcp.<server_id>.token}` 引用，实际值进用户级密钥库，对外接口继续掩码。
- 配额与清理：npm 缓存默认 2 GB/用户，按 server 做 LRU；stdio 日志 5 MB × 3 轮转；空闲 5 分钟回收子进程与连接。
- 多 worker 限制：配置写入用文件锁 + 原子替换；连接池只在单 worker 内有效，多 worker 部署前必须固定单 worker，或把 MCP 连接收口到独立网关进程。
- 迁移：`<PROJECT_ROOT>/.mcp/users/*` → `<HARNESS_HOME>/mcp/users/*/runtime/*`；旧 `mcp/servers.json` 只保留为 `<HARNESS_HOME>/mcp/servers.template.json`，不再作为运行时配置。
- 索引：`servers.json` 直接作为服务索引，运行态状态放内存，不额外建表。

### 4.2 SKILL

**现状**

- 内置技能：`src/agent/skills/main`，源码模式直接作为可写技能库。
- 用户技能库：`users/{user_id}/skills`，首次访问整目录复制内置技能；停用移动到 `skills-disabled`。
- 子 Agent 技能：`skills/subagents/{agent}/{skill}`，与主技能同在用户库下。

问题有三个：N 个用户复制 N 份内置技能；内置技能升级后用户副本不会更新；沙箱预热同步的是全局 `SKILLS_ROOT`，而不是用户技能库。

**目标**

```text
<HARNESS_HOME>/skills/builtin/{skill}/
<HARNESS_HOME>/skills/users/{user_id}/main/{skill}/
<HARNESS_HOME>/skills/users/{user_id}/subagents/{agent}/{skill}/
<HARNESS_HOME>/skills/users/{user_id}/skills-disabled/
<HARNESS_HOME>/skills/users/{user_id}/skills-state.json   # builtin_version + 每个技能的内容哈希
```

- 内置技能只读共享；用户目录只放「用户自己创建的 + 被用户改过的」技能，未改动的内置技能不复制，读取时先用户目录、再 builtin，等价于 overlay。
- `skills-state.json` 记录内置版本与内容哈希：升级只刷新哈希未变的副本，用户改过的保留并标记 `local-modified`。
- 沙箱同步只同步合并后的用户视图；预热实例不能再同步全局 `SKILLS_ROOT`，否则预热环境里是共享技能视图，存在跨用户读到同一份技能内容的风险。
- 卸载仍是硬删除；停用仍是移动目录，不引入第三套状态。
- 配额：默认 200 MB / 用户、2000 个文件；超限拒绝安装并提示清理。
- 迁移：现有 `USER_DATA_DIR/skills` 先作为 `skills/builtin` 的种子；若只有一个历史用户，同时复制到 `skills/users/{uid}/main`，多用户场景保留 `skills/legacy` 只读兜底并在设置页提示人工确认。

### 4.3 Plugin

插件是 v1.1 新增模块，发布前直接把路径定死，不要重复 MCP 和技能的两套路径问题。

```text
<HARNESS_HOME>/plugins/builtin/{plugin_id}/{version}/
<HARNESS_HOME>/plugins/users/{user_id}/{plugin_id}/current.json
<HARNESS_HOME>/plugins/users/{user_id}/{plugin_id}/versions/{version}/
<HARNESS_HOME>/plugins/users/{user_id}/{plugin_id}/data/
<HARNESS_HOME>/plugins/users/{user_id}/{plugin_id}/logs/
<HARNESS_HOME>/plugins/users/{user_id}/plugins-disabled/{plugin_id}/{version}/
```

- 用户目录只放版本、`data/`、`logs/`；非敏感配置统一存 PG `plugin_config`，不再落一份 `config.json`。
- 内置插件只读共享，所有用户默认拥有；用户侧只落启停状态（PG `plugin_user_state`），不复制代码。
- 用户插件按 `user_id` 全隔离：版本、数据、日志、进程、密钥都不跨用户；插件进程工作目录固定在该插件目录下。
- 远程插件不落包：endpoint 与 protocolVersion 写 `plugin_install`，非敏感配置写 `plugin_config`，密钥进用户级密钥库；目录里没有它的版本目录。
- 配额：默认 1 GB / 用户、最多 50 个插件、最多 8 个并发插件进程；超限拒绝安装。
- 版本保留最近两个；卸载删版本与进程，`data/` 与审计保留，用户可手动清理。
- 项目级插件仍在 `.commonharness/plugins/`，不进入用户目录，只在沙箱内运行。
- 数据库四张表 `plugin_install`、`plugin_user_state`、`plugin_config`、`plugin_audit` 均按 `user_id` 建索引；磁盘目录与表记录一一对应，删除走审计。
- 打包脚本负责把 `src/agent/plugins/builtin` 复制到 `<HARNESS_HOME>/plugins/builtin`，版本号与主程序一致；发布目录只读时整体落到 `USER_DATA_DIR` 回退根，不在只读目录里写运行数据。

**发布前要做的三件事**

1. 统一基准：新增 `PUBLISH_PROGRAM_PATH`（打包取 exe 目录，源码取仓库根），解析出可写的 `HARNESS_HOME`（不可写回退 `USER_DATA_DIR`）；MCP / SKILL / Plugin 全部相对 `HARNESS_HOME` 布局，两种模式完全一致。
2. 写一次性迁移脚本：MCP 运行态、技能库、旧 `USER_DATA_DIR/skills` 按本节规则搬到新布局，幂等、可回滚。
3. 加配额与清理任务：MCP npm 缓存 LRU、日志轮转、插件旧版本清理、用户目录统计接口（控制台设置页展示）。

## 五、命令系统

现在，用户可以输入 ’/‘ 来展开命令列表了。命令系统设计参考MineCraft的命令系统。
命令模块旨在帮助用户快速准确的构建输入提示词，从而更精确的指定AI的行为。

所有命令在输入/ 是，应给予智能提示与ENter 或者Tab键补全。

命令模式可以在系统设置内开启或者关闭。

基础命令：
- /help 显示命令列表
- /delete 删除当前会话，走已有的API接口，前端照常提示是否删除
- /delete -f 直接删除
- /withdraw 回撤最新对话
- /rag 查看当前连接的知识库、连接状况、连接时间表格

调用资源类命令
- /agent <agent-name> [-team] [team_name] 指定下次对话使用什么智能体，用户输入/agent时，前端应展示出来所有可用的智能体列表，用户选择列表项来快速填入name参数，也可以自己填名字，支持文本提示与快速补全名字.
