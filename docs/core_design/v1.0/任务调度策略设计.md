# 任务调度策略设计

Time: 2026/11/13

---

Agent 平台的任务调度，核心矛盾在于：LLM 的“规划能力”在短任务上够用，但在长任务、多任务、模糊任务上并不可靠。因此调度策略的设计关键不在于让模型“更聪明地规划”，而在于把规划与执行分离，用显式的任务状态、依赖关系和中断检查点来承载调度逻辑，让模型在结构化的框架内做有限度的决策。

## 任务一般是抽象的、无法预测的。
任务，即完整目标。目标达成之前，不论是人还是AI，都无法准确给出完美的执行步骤。  

其次，当遇到很长的业务描述时，如何划分任务阶段，并分析出任务难度（复杂度）、资源需求等**可控因素**，同时处理好耗时、质量等非可控因素，才是任务规划的一个难点。

## 问题一：长任务分批 + 优先级
长任务的根本风险不是“慢”，而是“断”——一次超时、一次上下文溢出，前面跑了半小时的进度可能全部作废。分批不是可选项，而是长任务调度的前置条件。

分批的依据：可恢复性，而非步骤数
不要把“分批”理解为按固定步数切分。有效的分批单位是可恢复的里程碑：每完成一个子目标，状态可以被持久化，中断后能从最近检查点恢复，而非从头再来。具体做法：

Planner 生成带依赖关系的任务 DAG，而非线性列表。DAG 的价值在于：执行器可以识别哪些子任务可以并行、哪些必须串行等待依赖完成，调度决策由此有了结构性依据，而不是靠模型“感觉先做哪个”。

每个节点执行完毕即落检查点，记录“做了什么、产出了什么、下一步的输入是什么”，且检查点要包含验证方法（如输出行数、关键字段非空），恢复时先验证再继续，避免带着脏数据往下走。

分层上下文管理：长任务中工作记忆和长期记忆分开维护，避免每次恢复都从数据库重新拼装推理链，导致软信号和置信度信息丢失。

优先级从哪里来
长任务的优先级分两层：

层一：结构优先级（硬约束） 。由 DAG 的依赖关系决定——被阻塞的任务即使“更重要”也无法先执行。这一层的优先级不需要模型判断，是确定性的。

层二：价值/紧急度优先级（软判断） 。在可执行的任务集合中，用 P0–P3 分级，优先级可以由 Agent 基于任务目标、截止时间、下游影响范围等因素自评，但必须允许用户覆盖。关键设计是：不要问用户“哪个更重要”，而是让 Agent 给出带理由的优先级排序，用户只需确认或调整。从零追问的成本远高于“确认/修正”一个已有草案。

一个值得注意的工程细节：当高优先级任务到达时，系统需要支持抢占。如果 Agent 正在等待某个远程调用返回，单纯靠轮询无法及时响应新到的紧急任务；可行方案包括在等待期间同时检查积压队列，或将累计等待时间计入优先级评分，使低优先级任务因“老化”而获得执行机会。

分批的告知方式
用户不需要看到 25 步的超细计划——那会造成认知过载。正确的粒度是分层摘要：先给出 3–5 个阶段级里程碑及其预计产出，用户确认后再展开当前阶段的详细步骤。研究显示，分层呈现执行计划能让用户先扫描结构、只在可疑处下钻，诊断效率显著优于逐步骤的线性日志。

## 问题二：无顺序待办事项，是否向用户提问
应该提问，但不是把所有事项抛回给用户排序。 向用户提问的核心设计问题是：在有限的人类注意力下，问什么、什么时候问、问多少。

先尝试推断，再问缺口
直接问“这些事项哪些更重要”会把调度负担完全转嫁给用户，而且用户往往也说不清——他们能判断的是约束和后果，不是抽象的优先级数值。更有效的路径是：

Agent 先做结构性推断：从事项的截止时间、依赖关系、涉及方、历史模式中推导出一个初始排序。能推断的字段直接填默认值，以草案形式呈现。

只问“一旦错了后果严重”的关键不确定点，且最多 3 个。这是硬约束：超过 3 个问题，用户放弃回答的概率急剧上升。问题的形式应该是决策型的，而非开放式排序型的，例如：“事项 B 的下游依赖是否必须在今天内解锁？”而不是“B 和 C 哪个更重要？”

澄清本身也需要优先级。当多个待确认问题同时存在时，先答哪个不取决于单个问题自身的“重要性”——一个孤立看很紧急的问题，如果它的答案不影响其他任务的推进，就不应该优先占用人类注意力。最优的提问顺序依赖于整个待办组合的状态，而非任务局部属性。工程上可以用近似策略：优先问那些答案会改变多个下游任务状态的问题。

何时不问，直接执行
有一类情形不需要向用户提问：当事项之间不存在硬依赖，且后果可逆时。此时 Agent 可以先按推断的优先级执行，在执行过程中“边做边确认”——每完成一个低风险批次，把结果和下一步建议呈现给用户，用户可以在任意检查点介入修正。这比前置的重度确认流程更高效，也避免了“为了安全把所有步骤都塞人工”的反模式。

## 区分“可控”与“不可控”：一个可操作的表征框架

你追问的核心是：在阶段划分之后，如何分析出难度、资源需求这些“可控因素”，并处理好耗时、质量这些“不可控因素”。这里的关键洞察是：可控与不可控并非任务的内在属性，而是相对于 Agent 当前的知识和资源而言的。同一个任务，对具备相关因果模型的 Agent 是可控的，对缺乏该模型的 Agent 则是不可控的。

MIT 的 Kris 在关于任务内在复杂度与难度的形式化工作中给出了一个有启发的框架：任务难度 D 可以表达为 D=C*I*R*N_t,
其中 C 是控制器的能力，I 是任务的内在复杂度（intricacy） ，R 是可用资源，N_T是变换器噪声（感知和执行的不可靠性）。这个公式的价值在于，它把“难度”分解成了几个可以分别对待的维度：

|维度|性质|在 Agent 规划中的含义
|---|---|---|
|内在复杂度 I|	相对可控（可通过分解降低）|	任务包含的独立元素数量、元素间耦合程度、是否需要推理链。分解动作本身就是在降低有效复杂度。|
|资源 R|	可控（可分配、可预算）	|Token 预算、工具调用次数上限、累计执行时间。这些是规划时可以显式分配和约束的量。|
|变换器噪声 N_T|部分可控（可通过冗余降低，无法消除）|	LLM 输出的方差、工具调用的失败率、环境反馈的延迟。这是耗时和质量不确定性的结构性来源。|
|控制器 C|	相对固定（当前 Agent 的能力边界）|	在当前阶段，Agent 的推理和工具使用能力是一个给定约束。

“资源 R”是可控性的锚点。无论任务多么抽象，你总是可以在规划阶段声明一个预算包络：这个阶段最多消耗多少 token、允许多少次工具重试、容忍多长的 wall-clock 时间。即使你无法预知“完成这个阶段需要多少步”，你也可以设定“在给定预算内，Agent 应该做到什么程度的进展”。  

## 处理不可控的耗时与质量：约束驱动 + 储备机制
耗时和质量之所以“不可控”，是因为它们不是被规划出来的，而是在执行中涌现的。你无法在规划阶段“决定”一个子任务耗时 30 秒还是 3 分钟，但你可以管理耗时和质量对整体成功概率的影响。

当前 Agent 研究中的一个核心进展，是把预算和时间从“事后度量”变成成功条件本身。在一篇关于工作流执行的论文中，目标函数被明确写为“在截止时间 
D
D 之前完成，且总成本不超过预算 
B
B”的约束完成概率。超过预算或截止时间，不再是“效率低一点”，而是任务在形式上失败。

在这种框架下，处理不可控因素的核心机制是 “储备”（reserve） 。ReserveGate 的工作展示了这一思路：在每个决策点，控制器不仅评估当前动作的即时收益，还会计算一个动态储备量——必须为下游的未知需求保留多少 token 和时间资源。储备在早期被严格锁定，随着已完成的进度比例逐步释放，在最后阶段才完全可用。这相当于在不可预测的执行流中，为“耗时超预期”和“质量不达标需要重试”预留了对冲空间。

质量的处理遵循类似的逻辑。质量不是一个可以在规划阶段“设定”的标量，而是一个需要通过验证检查点来管理的涌现属性。在滚动波的每个“波次”边界，插入一个验证门：如果当前阶段的输出未达到预设的验收标准，触发的是局部重规划（只调整剩余部分），而非全盘推翻。验证标准本身必须是可判定的（字段非空、接口返回码、格式匹配），因为 LLM 对自身输出的自验证是出了名地不可靠。

## Langchain的Deepagent内置的任务规划能力
LangChain 版 deepagents：规划是“可选能力”，形态更轻
LangChain 生态中的 deepagents 是一个开源框架，其内置规划工具是 WriteTodos——让主 Agent 创建一个结构化的待办列表（todo list），用来分解和跟踪任务，然后再通过 TaskTool 把子任务委派给专门的子 Agent。官方文档将任务规划列为 “可选能力”（optional capability），不是强制的内置架构。这种规划更接近“结构化任务分解 + 子智能体编排”，而不是严格的 HTN 形式体系。
