两次异常不是独立故障，而是同一份被污染的历史消息状态导致的连续失败：第一次运行在压缩后写入了错误的切点指针，第二次运行重放该指针，1 秒内再次 400。

## 二、现象与直接原因

模型服务返回：

```
openai.BadRequestError: Error code: 400 - Messages with role 'tool' must be a
response to a preceding message with 'tool_calls'
(request_id: 8a10f9ff-5ab7-44fc-b15f-c225479d11ff)
```

原因：压缩后实际发给模型的消息按如下规则重建：

```
effective_messages = [summary_message] + state_messages[cutoff_index:]
```

当 `cutoff_index = 209` 时，`state_messages[209]` 是一条 `ToolMessage`（`tool_call_id = call_00_6pjWuf4mRtGKInGakc3u5480`），而发起它的 AI 消息在索引 208，被切掉了。重建后的列表以一条“无前置 `tool_calls` 的 tool 消息”开头，模型服务直接拒绝。

checkpoint 证据：

| 时间       | step | 消息数 | cutoff  | cutoff 处角色   |
| -------- | ---- | --- | ------- | ------------ |
| 19:37:59 | 533  | 519 | 151     | ai（正常）       |
| 19:38:01 | 534  | 520 | **209** | **tool（错误）** |
| 19:39:21 | 544  | 522 | 209     | tool         |

关键时序：step 534 的模型调用**成功了**（产出了 519 号 AI 消息），说明当时发给模型的消息是合法的；但同一次调用写回的指针是错的。下一次模型调用才 400——这个“先成功、下一秒失败”的时序，说明坏的不是消息内容，而是持久化的索引。

## 三、根因

### 3.1 双层摘要中间件

`create_deep_agent` 在主栈中无条件注入内置摘要中间件（`deepagents/graph.py` 第 886-891 行）：

```python
deepagent_middleware.extend([
    create_summarization_middleware(model, backend),
    PatchToolCallsMiddleware(),
])
```

自定义中间件随后按 `.name` 合并：名字相同则**原位替换**，不同则**追加**（`deepagents/graph.py` 第 204-238 行）。项目里的 `HarnessContextCompactionMiddleware` 继承自摘要中间件，但类名不同，因此没有替换内置实例，而是被追加为第二层摘要。

```python
class HarnessContextCompactionMiddleware(SummarizationMiddleware):
@property
def name(self) -> str:
return "SummarizationMiddleware"
# 原本HarnessContextCompactionMiddleware这个中间件的名字和SummarizationMiddleware不同，这就导致了出现两次替换摘要信息的bug，这里把HarnessContextCompactionMiddleware改为同名就解决了。
```

实际链路（由外到内）：

```
Skills → Filesystem → SubAgent → Summarization(内置) → PatchToolCalls
        → [业务中间件...] → Summarization(Harness) → ... → Model
```

内置层的阈值是 `0.85 × 1M = 850,000` tokens，本次不会触发压缩；但它在“不压缩”分支里仍会把已应用过摘要事件的消息列表透传给下游（`deepagents/middleware/summarization.py` 第 1543 行）：

```python
return await handler(request.override(messages=truncated_messages))
```

Harness 层因此拿到的是“已压缩视图”，而不是原始 state。

### 3.2 压缩事件被应用了两次

Harness 层默认 `request.messages` 就是原始 state，于是把同一个 `_summarization_event` **又应用了一次**。设：

- 原始 state 列表 `S`（519 条）
- 已有事件切点 `P = 151`
- 摘要消息 `H`

| 操作       | 列表                   | 长度  |
| -------- | -------------------- | --- |
| 原始 state | `S`                  | 519 |
| 外层应用一次   | `E = [H] + S[151:]`  | 369 |
| 内层再应用一次  | `E2 = [H] + E[151:]` | 219 |

内层在 `E2` 上计算切点，得到 `k = 59`（该值合法，对应一条 AI 消息）。但写回 state 时，框架只按“应用过一次”换算：

```python
# deepagents/middleware/summarization.py 第 848 行
return prior_cutoff + effective_cutoff - 1
# 151 + 59 - 1 = 209
```

### 3.3 索引空间错配的含义（带数字例子）

“索引空间”指同一个列表在不同代码层看到的坐标系统。`cutoff_index` 是整数，本身没有语义；它的语义取决于“这个整数是在哪个版本的列表上数出来的”。

| 坐标空间        | 列表内容            | 索引 59 实际指向                 |
| ----------- | --------------- | -------------------------- |
| 原始 state    | `S[0..518]`     | `S[59]`                    |
| 应用一次事件 `E`  | `[H] + S[151:]` | `S[151 + 59 - 1] = S[209]` |
| 应用两次事件 `E2` | `[H] + E[151:]` | `S[301 + 59 - 1] = S[359]` |

映射公式（`i >= 1`，索引 0 被摘要消息占用）：

```
E [i] = S[151 + i - 1]
E2[i] = E[151 + i - 1] = S[301 + i - 1]
```

于是：

```
内层算出的 k = 59             （E2 坐标系）
框架写回 cutoff = 151+59-1 = 209（误当成 E 坐标系）
正确的 state 坐标 = 301+59-1 = 359
偏移量 = 359 - 209 = 150 = P - 1
```

每多应用一次摘要事件，列表就净缩短 `P - 1` 条（151 条消息被 1 条摘要替换）。**两个坐标系的原点相差 150，写回时只换算一次，所有指针整体左移 150 位。**

### 3.4 为什么第一次调用没报错

内层真正发给模型的是：

```
preserved = E2[59:] = S[359:]
```

`S[359]` 是一条 AI 消息，其后紧跟对应的 tool 结果，序列合法，所以 step 534 调用成功。

写回 state 的指针却是 209：

```
下次调用重建：[summary] + S[209:]
S[209] 是 ToolMessage → 列表以孤立 tool 消息开头 → 400
```

### 3.5 为什么自动重试无效

`RunSupervisor` 依据异常分类决定是否重试。`OpenAIInvalidRequestError` 被判定为 `fatal`（确定性错误），不重试，直接终止并把错误抛给前端（`src/agent/runtime/supervisor.py` 第 124-165 行）。

即使重试也没用：坏指针已经写进 checkpoint，每次重放都会得到同样非法的消息列表。19:39 用户发送“继续，内部异常了”，1 秒内以相同指纹再次失败，就是这个原因。

相关的框架内容：

LangChain 的 DeepAgent 框架在处理消息时，确实可以类比为一种 **“数组 + 指针”** 的混合管理模式。其中，**“数组”** 是基础的消息序列容器，而 **“指针”** 则是一种关键的**上下文优化机制**，用于在数组内部用轻量级的引用替代庞大的原始数据，以应对大模型有限的上下文窗口。

### 📚 “数组”：消息的基础容器

DeepAgent 的核心状态中，`messages` 字段本身就是一个**有序的数组（列表）**，严格按照时间顺序记录着用户、AI和工具之间的每一次交互。

这个数组里通常装载着 LangChain 定义的四类消息对象：
*   **`SystemMessage`**：承载系统指令与行为约束。
*   **`HumanMessage`**：记录用户输入。
*   **`AIMessage`**：记录模型的输出，包括文本和发起的 **工具调用（tool calls）**。
*   **`ToolMessage`**：承载工具执行后返回的结果。

关键在于，这个数组**并非一个可以随意切片的普通列表**。它是一份 **“带配对约束与顺序约束的协议记录”**。`AIMessage` 中发起的每一个工具调用，都有一个唯一的 `id`，必须与后续 `ToolMessage` 中响应的 `tool_call_id` 严格配对。如果随意截断数组，破坏了这种配对关系，模型将无法理解，甚至会产生幻觉。

### 🔗 “指针”：上下文的高效“卸载”机制

当对话历史或工具返回的结果过大时，直接塞进 `messages` 数组会迅速耗尽模型的上下文窗口。为此，DeepAgent 引入了 **“指针卸载”（Pointer Offloading）** 机制，这正是在数组内部实现“指针”思想的核心。

其运作逻辑是：当单个工具调用的结果超过阈值（默认约 **20,000 个 token**），或者整个会话上下文使用量超过模型窗口的 **85%** 时，系统不会再将完整的原始数据（如一份数万行的数据表）留在 `messages` 数组里。

取而代之的是，系统会将完整的原始内容**卸载并保存到外部文件系统**中，然后在 `messages` 数组的对应位置，用一个**轻量级的“指针”来替换**庞大的原始内容。

这个“指针”通常表现为：
*   一个**文件路径引用**，并附带原始内容的**前 10 行预览**，方便模型快速判断内容是否相关。
*   一个指向磁盘文件的引用标识，例如 **“指向磁盘文件的指针”**，明确告知模型完整数据的位置。

这样，`messages` 数组里保留的不再是“数据本身”，而是“数据的地图”。模型在需要时，可以根据这个“指针”（文件路径）去外部存储中按需读取详细内容，从而在不牺牲信息完整性的前提下，极大地节约了宝贵的上下文窗口。

### 🤝 “指针”思想在子代理协作中的延伸

这种“指针”式的思维也体现在 DeepAgent 的子代理（Subagent）协作中。当主代理将任务委派给子代理时，它**不会将完整的对话历史数组直接传递过去**。相反，主代理会构造一个**全新的、精简的输入**，通常只是一条包含任务描述的 `HumanMessage`，作为一个“指针”来启动子代理。

子代理在自己的上下文中完成任务后，也**只将最终的结论性消息**返回给主代理，主代理再将其转换为 `ToolMessage` 追加到自己的 `messages` 数组中。这个过程通过隔离和精简信息流，避免了子任务的大量中间过程污染主代理的上下文数组。

总结来说，DeepAgent 的消息管理可以看作是：用 **`messages` 数组**来维持严格的交互协议与顺序，同时用**“指针卸载”** 策略，将数组中体积过大的“值”替换为指向外部存储的“引用”，以此在有限的上下文窗口内，实现长时间、复杂任务的稳定运行。
