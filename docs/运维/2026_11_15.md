## [BUG-1] MCP Server 重启后旧会话未淘汰，报 "Session terminated"

| 项目 | 内容 |
| --- | --- |
| 模块 | `src/agent/mcp`（连接池 / 调用路由 / 运行时状态机） |
| 发现人 | 测试组（集成模式、带鉴权的自建 MCP 服务联调） |
| 严重级别 | P2（可用性抖动，但会被放大成"服务不可用、需人工介入"） |
| 状态 | 已修复，待测试回归 |

---

### 1. 现象

- 集成的 MCP 服务项目（用户自有后端封装的 MCP）重启后，Harness 后端继续使用重启前建立的
  `streamable_http` 会话。
- 重启后第一次调用返回：

  ```json
  {"ok": false, "error": {"code": "MCP_CALL_FAILED", "category": "permanent", "retryable": false}}
  ```

  底层报错为 `Session terminated`（JSON-RPC 32600），服务状态被置为 `Failed`，工具从模型可见清单中消失。
- 恢复只能人工点"探测 / 重启"，或在设置页重新保存配置；重启瞬间的调用必现。
- 该现象只在**需要鉴权**的 MCP 服务上稳定复现。

### 2. 触发条件

1. `transport = streamable_http`（有状态传输）；
2. 本进程已成功 `initialize` 并缓存了会话；
3. 对端进程重启 / 容器滚动发布 / 凭据轮换；
4. 重启后发生第一次工具调用（或健康检查 `ping`）。

### 3. 根因

#### 3.1 为什么 URL 没变，连接池里的连接却失效了

连接池缓存的不是 URL，而是 **MCP 协议会话 `ClientSession`**：

- `pool_key` 由 `transport + connection(url/headers)` 计算（`types.py::ServerConfig.pool_key`）。
  对端重启后 URL 没变 → key 不变 → 直接命中**旧会话**。
- MCP 的 streamable HTTP 是**有状态协议**：`initialize` 时服务端签发 `mcp-session-id`，
  并在**内存**中保存会话（`mcp.server.streamable_http_manager` 的 `_server_instances`）。
  之后每个请求都必须携带这个 id。
- 服务端重启 → 内存会话表清零 → 客户端携带旧 id → 服务端按规范返回 **404 "Session not found"**
  → MCP SDK 转换成 JSON-RPC **32600 "Session terminated"**。
- **鉴权场景必现的原因**：启用鉴权后服务端必须使用有状态会话，并把会话与凭据主体绑定
  （`_session_owners`）；重启后会话归属必然失配，只能返回 404。无鉴权的服务常用 stateless
  模式（每个请求新建 transport），因此不会暴露该问题。

#### 3.2 Harness 侧的两个缺陷

**a. 连接池没有会话失效处理**
池项只在 worker 退出时才会被标记 `closed`。收到 404 后 worker 不退出，`closed` 始终为 False，
于是失效会话一直留在池里被复用；只能等 SSE 长连接自行断开或空闲 TTL（默认 300s）回收。

**b. 错误分类把可自愈事件判成永久故障**
SDK 的 `McpError`（`mcp.shared.exceptions`）与 Harness 自己的 `McpError`（`agent.mcp.types`）
同名但不同类，`router.py` 的 `except McpError` 接不住它，落到 `except Exception` →
`classify_exception` 兜底：错误文本 `"Session terminated"` 不匹配任何 token →
`PERMANENT / retryable=false` → `_apply_failure` 把服务置 `FAILED` 并注销工具。
一次"重连就能好"的抖动，被升级成"服务不可用、需人工介入"。

#### 3.3 放大因素

健康检查把这次确定性事件当成普通抖动，需要累计 `failure_threshold=3` 次才处理；
期间状态与工具清单已经在抖动，用户侧感知为"偶发失败 + 工具消失"。

### 4. 与测试反馈的比对

> 源 BUG（测试反馈）：
> a. 连接池没有会话失效处理：池里缓存 `streamable_http` 会话，但 404 后没有
> 「判定失效 → 关闭 → 重建 → 重试」，只有等 SSE 长连接自己断开或空闲 TTL 才回收。
> 重启瞬间的调用会直接撞上 404。
> b. 错误分类把可自愈事件判成永久故障：SDK 的 `McpError` 和 Harness 自己的 `McpError`
> 同名但不同类，所以 `router.py` 的 `except McpError` 根本没接住它，落到兜底的
> `classify_exception` → `PERMANENT / retryable=false`；随后 `_apply_failure` 把服务状态置
> `FAILED` 并注销工具。

结论：**两条判断方向都正确，与最终定位一致**，细节上有三处需要补充：

| 测试判断 | 核实结果 | 补充说明 |
| --- | --- | --- |
| a. 池未处理会话失效 | 成立 | 准确说不是"只能等 TTL"：10s 周期的健康检查 `ping` 也会撞上，但当时同样被误判为永久故障，因此最终表现仍是只能人工介入 |
| b. 错误分类误判为 permanent | 成立 | 精确表述：真正缺的是"会话失效"这一分类。错误文本没有任何可匹配 token，即使 `except McpError` 接住也会在 `classify_exception` 里提前返回，不会自动重连 |
| — | 补充 | 测试未覆盖：**鉴权与会话绑定**解释了为什么必现在鉴权场景；**重连窗口内状态被误标 Dormant** 的问题也在本次一并修复 |

### 5. 修复内容

| 文件 | 改动 | 效果 |
| --- | --- | --- |
| `client_registry.py` | 新增 `is_session_lost()`；worker 收到会话失效错误后退出并标记 `closed`；`acquire` 过滤 worker 已退出的池项；新增 `discard()` | 失效会话不再被复用；`discard` 按对象身份摘除，避免并发时误杀同 key 新建的会话 |
| `router.py` | 新增 `MCP_SESSION_LOST`（`TRANSIENT`）分类；调用命中时 `discard` 旧连接 → 重新 `acquire`（重新 `initialize` 拿新 `mcp-session-id`）→ 重放一次 | 对模型透明：重启后的第一次调用自动恢复，不再升级为 `FAILED` |
| `runtime.py` | 健康检查发现会话失效立即淘汰并进入重连；调用成功时把误标的 `Dormant` 纠正为 `Connected` | 后台自愈，不必等到 3 次失败；状态展示与实际一致 |

兼容性：代理工具对象与工具名不变，不需要重建 Agent 图；观测层新增事件 `mcp.session_lost`。

### 6. 验证

- 验证脚本：`useless/verify_mcp_restart_recovery.py`
  1. 启动 FastMCP streamable HTTP 服务，调用 `echo`；
  2. kill 进程，同端口拉起新进程（模拟集成方重启）；
  3. 再次调用 `echo`。

  结果：`Session terminated` 被识别并自动重连，**0.22s 内返回正常结果**，状态保持 `Connected`，
  连续 3 次稳定通过。
- 回归：`test/test_mcp_integration.py`（stdio / 子 Agent YAML / streamable HTTP）全部通过。

### 7. 运维处置手册

**判定是否为该问题**

- 服务状态：`Failed`，`error_code = MCP_CALL_FAILED`；
- 日志（`GET /mcp/servers/{server_id}/logs`）出现 `Session terminated` 或 `404`；
- 时间点与对端 MCP 服务发布/重启吻合，且服务为鉴权接入。

**修复后的预期行为**

- 日志应出现：`MCP 会话已失效，淘汰旧连接: server=... pool_key=...`、事件 `mcp.session_lost`、
  随后 `MCP 懒连接成功`；
- 服务状态保持 `Connected`，工具清单不变化，模型侧只看到一次正常结果。

**人工兜底**

| 操作 | 接口 | 说明 |
| --- | --- | --- |
| 重新探测 | `POST /mcp/servers/{server_id}/probe` | 强制重新建连并重新发现工具 |
| 重启连接 | `POST /mcp/servers/{server_id}/restart` | 关闭该服务在池中的连接，状态回到 `Dormant` |
| 查看日志 | `GET /mcp/servers/{server_id}/logs` | 观测层最近事件，含连接、状态变更、调用结果 |

状态含义：`Dormant` 未建连 / `Starting` 建连中 / `Connected` 正常 / `Degraded` 调用超阈值 /
`Pending` 等待退避重试 / `NeedsAuth` 需要重新配置凭据 / `Failed` 已放弃自动重试。

### 8. 已知边界与后续

- **长停机不会自动复活**：调用失败会按 4 次指数退避重试（约 1s/2s/4s/8s），超过后服务置 `Failed`，
  健康检查会跳过非 `Connected/Degraded` 状态，需要人工 `probe`。若集成服务启动时间超过 ~15s，
  建议调大该服务的 `retry.max_attempts / max_delay_ms`，或后续为 transient 失败的 `Failed` 服务
  增加低频复活探测。
- **401 不自动恢复**：如果对端连凭据存储也是内存态，重启后返回 401 而非 404，属于真实的
  `NeedsAuth`，需要重新配置 header / 凭据。
- **滚动发布需要粘性会话**：同一 URL 后挂多个实例时，`mcp-session-id` 只在创建它的实例上有效。
  没有粘性会话会表现为反复 404 → 重连，建议网关按会话粘滞，或改用单实例发布。
- **健康检查间隔**：`HealthPolicy.interval_ms` 当前未生效，`_health_loop` 固定 10s 轮询，
  修改配置不会改变实际探测频率。

## [BUG-2] MCP 配置修改只写入用户副本，不落共享默认配置

| 项目 | 内容 |
| --- | --- |
| 模块 | `src/agent/mcp`（配置存储）+ `src/agent/user_data.py` |
| 发现人 | 测试组（多用户部署场景） |
| 严重级别 | P3（配置语义问题，不阻塞单用户使用） |
| 状态 | 已知问题，**决定不修复**（业务诉求与通用平台定位不一致） |

### 1. 现象

多用户部署时，开发把自有 MCP 配置放在项目根目录 `mcp/servers.json`，作为“所有用户的默认服务”。
随后在 MCP 设置页修改某个服务（例如把它标记为“集成项目”），保存成功、当前用户界面也生效，
但 `mcp/servers.json` 没有变化；其他已存在的用户和新用户都拿不到这次修改。

### 2. 原因（已核实，不是写入失败）

- 每个用户首次访问时，`user_data.user_mcp_config_path()` 会把共享的 `mcp/servers.json`
  **复制一次**到 `users/<uid>/mcp/servers.json`（`_copy_file_once`，目标已存在就跳过）。
- `get_mcp_runtime()` 创建的 `MCPRuntime` 以这个**用户副本**作为 `McpConfigStore` 的 `path`。
- 所有管理接口（`upsert_server` / `import_servers` / `delete_server` / `set_enabled`）
  都只写 `self.path`，即用户副本；共享默认文件只在“新用户首次访问”时被读取。
- 因此：编辑看起来“保存成功”，实际写到了 `users/<uid>/mcp/servers.json`；
  共享 `mcp/servers.json` 始终停留在开发最初放入的内容，已播种过的用户也不会再同步。
- 佐证：当前工作区里 `mcp/servers.json` 与 `users/anonymous|alice/mcp/servers.json` 内容一致
  （都含 `integration: true`），是因为这些用户副本是在共享文件更新之后才播种的，
  并不代表 UI 修改会回写共享文件。

### 3. 影响

- 多用户部署下，“在 UI 里改一次、所有用户默认拥有”不成立；
- 老用户配置与共享默认会长期分叉，排查问题时容易误判成“配置没保存”；
- 不影响单用户使用，也不影响 MCP 连接与会话逻辑。

### 4. 处理决策

**不修复**。这是“把一个具体项目的默认服务分发给所有用户”的业务诉求，与平台当前
“每用户独立 MCP 配置”的通用设计冲突；若做成全局写穿，任意用户的修改都会影响其他用户，
反而破坏通用性。

### 5. 现行替代做法（不改代码）

1. 开发直接维护共享文件 `mcp/servers.json`，作为所有人的初始默认；
2. 需要让已存在的用户重新拿到共享配置时，备份后删除对应用户的
   `<USER_DATA_DIR>/users/<uid>/mcp/servers.json`，下次访问会重新播种
   （该用户在 UI 里的改动会一并丢失）；
3. 也可以在共享文件变更后，让各用户在自己的设置页重新保存一次。

### 6. 如果将来要做（决策记录）

- 方案 A：MCP 配置全用户共享一份（最贴合单用户定位，但取消个人隔离）；
- 方案 B：双写 + 加载时把共享新增服务合并进用户副本（保留个人配置，需定义冲突规则）；
- 方案 C：显式“发布为共享默认”操作（语义清晰，但不是全自动）。
