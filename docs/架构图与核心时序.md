# 架构图与核心时序

> 目标：用图把本项目的**模块边界、调用方向、状态归属**讲清楚。
> 读完后你应该能回答三个问题：
> 1. 一个 HTTP 请求进来后，经过了哪些模块？
> 2. 沙箱、PostgreSQL、Agent Protocol 分别在哪一步被使用？
> 3. 中断、异步任务、技能同步失败时，状态最终落在哪里？

| 唯一持久化口径 | PostgreSQL | Checkpoint、用户记忆、会话索引、任务归属 |

**看图要点**

1. API 层**不直接构图**：它只通过 `AgentLoader` 拿“某用户已缓存的图”。
2. Agent 层**不直接连数据库**：它只通过 `backend` 读写，路由由 `CompositeBackend` 决定。
3. 沙箱和 PostgreSQL 是**并列的两个后端**，不是包含关系。
4. 异步子 Agent 是**另一个进程/服务**，主图只负责提交任务和轮询结果。

```mermaid

    APP->>LOADER: lifespan 启动
    LOADER->>CFG: create_async_persistence()
    CFG->>PG: 建立 Store / Saver 连接
    CFG->>PG: store.setup() / checkpointer.setup()
    PG-->>CFG: 表结构就绪
    CFG-->>LOADER: store, checkpointer

    LOADER->>SM: SandboxManager(store)
    LOADER->>SM: initialize()

    alt 已配置 OPEN_SANDBOX_API_KEY
        SM->>SB: 后台调度一个预热沙箱
        SB-->>SM: 预热实例（技能同步完成后才发布）
    else 未配置
        SM->>SM: 记录警告，禁用预热和执行
    end

    LOADER->>HR: ThreadHistoryReader(checkpointer)
    HR->>HR: 构建只读图（不调用模型）
    LOADER-->>APP: 初始化完成

    APP-->>OP: 开始接收请求
    Note over APP,SB: 启动阶段不创建用户沙箱；首次请求才按 user_id 分配
```

**看图要点**

- 启动只做三件事：连 PostgreSQL、调度预热、构建只读历史图。
- 预热沙箱是**无主的**：没有写用户绑定；分配时才和 `user_id` 关联。
- 没有 `OPEN_SANDBOX_API_KEY` 时服务仍能启动，但 `/chat` 会失败；`/health` 和只读接口不受影响。

## 4. 一次 SSE 对话的完整时序

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant API as chat.py
    participant L as AgentLoader
    participant SM as SandboxManager
    participant P as SandboxBackendProxy
    participant G as DeepAgents 图
    participant MW as 中间件
    participant M as 模型
    participant DB as PostgreSQL

    C->>API: POST /chat/stream
    Note right of C: message / thread_id / user_id

    API->>API: thread_id = 入参或 uuid4
    alt 传入了 thread_id
        API->>L: require_session(user_id, thread_id)
        L->>DB: Store 读取会话索引
        DB-->>L: 存在 / 不存在
        alt 不存在
            API-->>C: 404 会话不存在或无权访问
        end
    end

    API->>L: thread_operation(thread_id)
    Note right of L: 单进程内会话互斥，冲突返回 409
    API->>L: save_session(user_id, thread_id, 标题)
    API->>L: get_agent_for_user(user_id, username, thread_id)

    L->>L: 获取 user 级锁
    L->>SM: get_backend(user_id)
    SM->>SM: 缓存 / Store / 预热池 / 新建 决策
    SM->>P: 健康检查 + 续期
    alt 需要替换或首次创建
        SM->>P: replace_backend(新后端)
    end
    SM-->>L: proxy

    alt 该用户首次请求
        L->>G: create_main_agent(store, checkpointer, proxy)
        G->>G: CompositeBackend + 工具 + 子 Agent + 中间件
    end
    L-->>API: agent

    API->>G: astream(messages + values, subgraphs=True)
    G->>MW: abefore_agent
    MW->>P: SandboxSkillsMiddleware 增量同步技能
    MW->>G: 刷新技能索引

    loop 模型与工具循环
        G->>MW: wrap_model_call
        MW->>MW: 注入 user_id / 偏好路径
        G->>M: 发起模型调用
        M-->>G: 文本或 tool_calls

        alt 有工具调用
            G->>P: read / write / execute
            P-->>G: 工具结果
            G->>M: 带着工具结果继续
        end
    end

    G->>MW: aafter_agent
    MW->>M: 提取 query / preferred
    MW->>DB: aput (user_id,) /{user_id}/preferences.md

    G-->>API: messages / values 事件
    API-->>C: token / tool_start / tool_args / tool_result / tool_end
    alt 出现中断
        API->>G: aget_state 取根图 canonical 中断
        API-->>C: interrupt + done(interrupted=true)
    else 正常结束
        API-->>C: done(interrupted=false)
    end

    API->>L: 释放 thread_operation
```

**看图要点**

1. **会话锁先于 Agent 调用**：同一 `thread_id` 的并发请求会在入口被拒绝（409）。
2. **沙箱探测每次请求都做**：不是“构图时探测一次”。这样沙箱失效后，已缓存图仍能拿到新后端。
3. **图只构建一次**：`AgentLoader` 按 `user_id` 缓存；`thread_id` 只是 checkpoint 的 key。
4. **SSE 过滤子 Agent 事件**：`source != main` 的消息不发给前端，子 Agent 的内部过程不泄露。
5. **中断在流结束后 canonical 化**：从根图 `aget_state()` 取最终中断，避免子图中间 ID 导致恢复重放。

### 5.2 工具审批中断

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant API as chat.py
    participant G as 主图
    participant H as HITL Middleware
    participant Tool as 业务工具

    G->>H: 命中 interrupt_on 规则
    H->>G: interrupt(action_requests + review_configs)
    G-->>API: interrupt 事件
    API-->>C: interrupt_type=hitl_approval

    C->>API: resume {decisions: [...]}
    API->>G: Command(resume={decisions})
    G->>H: 读取 decisions
    alt approve
        H->>Tool: 原样执行
    else edit
        H->>Tool: 用 edited_action.name / args 执行
    else reject
        H->>G: ToolMessage(status=error, 包含拒绝原因)
    else respond
        H->>G: 跳过执行，用 message 作为工具结果
    end
    Tool-->>G: 结果
    G-->>API: 继续流式输出
```

**看图要点**

- `decisions` 的顺序和数量必须与 `action_requests` 一致。
- 恢复必须用**根图 checkpoint 的 canonical interrupt ID**；流里先出现的子图中断 ID 可能不是最终可恢复 ID。
- 暂停期间会话锁已释放；恢复时重新获取。

```mermaid
sequenceDiagram
    autonumber
    participant C as 客户端
    participant API as async_tasks.py
    participant L as AgentLoader
    participant APS as Agent Protocol
    participant G as 主图
    participant DB as PostgreSQL

    C->>API: GET /async-tasks/{task_id}?user_id
    API->>L: get_async_task_binding(task_id)
    L->>DB: Store 读取 async_tasks 绑定

    end

    API->>APS: runs.list(task_id)

    alt 非终态
        API-->>C: done=false, status=running
    else 终态
        API->>APS: threads.get_state(task_id)
        APS-->>API: values.messages
        API->>API: 提取最后 assistant 文本 / 错误

        API->>L: publish_async_task_result(task_id, content)
        L->>L: thread_operation(defer=True)
        L->>G: get_thread_state(主会话)
        alt 已完成投递
            L-->>API: true（幂等）
        else 主会话仍在中断 / 有 next
            L-->>API: false（稍后重试）
        else 可投递
            L->>G: aupdate_state(AIMessage id=async-task-result:task_id)

            L-->>API: true

        API-->>C: done=true, delivered=...
    end
```

**看图要点**

- 主 Agent 与异步子 Agent **共享沙箱**，但不共享 thread/run/消息历史。
- 结果投递使用固定消息 ID，因此重复轮询不会产生重复消息。
- 主会话正在中断时拒绝投递，避免覆盖暂停状态。
- Agent Protocol 只有一个图入口 `async_subagent`；新增子 Agent 只改注册表，不改 `langgraph.json`。

## 7. 沙箱管理与热替换

### 7.1 `get_backend(user_id)` 决策树

```mermaid
flowchart TD
    START["get_backend(user_id)"] --> LOCK["获取 user 级 asyncio.Lock"]
    LOCK --> CACHE{"进程内有 proxy?"}

    CACHE -->|"有"| HEALTH{"proxy.is_healthy()?"}
    HEALTH -->|"是"| RENEW["renew_sandbox 续期"]
    RENEW --> RETURN["返回现有 proxy"]

    HEALTH -->|"否"| RESOLVE["_resolve_backend"]
    CACHE -->|"没有"| RESOLVE

    RESOLVE --> LOOKUP["Store 读取 sandboxes/user_id/current"]
    LOOKUP --> HASID{"有 sandbox_id 且未确认死亡?"}
    HASID -->|"是"| CONNECT["SandboxSync.connect 重连"]
    CONNECT --> CONNHEALTH{"健康?"}
    CONNHEALTH -->|"是"| BIND["续期 + 写回 Store"]
    CONNHEALTH -->|"否"| CONNERR["抛错：保留原沙箱与持久化 ID"]

    HASID -->|"否"| WARM{"预热池有实例?"}
    WARM -->|"有"| WARMHEALTH{"健康?"}
    WARMHEALTH -->|"是"| BIND
    WARMHEALTH -->|"否"| DISCARD["丢弃预热实例"]
    DISCARD --> CREATE
    WARM -->|"没有"| CREATE["create 新建沙箱"]

    CREATE --> BIND
    BIND -.-> SYNC_NOTE["预热实例创建时已完成技能同步；按需新建实例由首次 run 的 SkillsSync 中间件同步"]
    BIND --> INSTALL{"已有 proxy?"}
    INSTALL -->|"有"| REPLACE["proxy.replace_backend(新后端)"]
    INSTALL -->|"没有"| NEWPROXY["创建 proxy 并缓存"]
    REPLACE --> RETURN
    NEWPROXY --> RETURN
```

**判定原则**

- 只有 **404 / TERMINATED / FAILED** 才算“确认死亡”，允许新建。
- 传输超时、健康检查失败不等于工作区丢失；优先重连并保留持久化 ID。
- 续期失败只告警，不触发换沙箱。
- 预热实例未分配，可直接丢弃；已分配实例只关闭客户端，不终止远端沙箱。

### 7.2 热替换时序

```mermaid
sequenceDiagram
    autonumber
    participant G as Agent 图
    participant P as SandboxBackendProxy
    participant SM as SandboxManager
    participant OLD as 旧 OpenSandboxBackend
    participant NEW as 新 OpenSandboxBackend

    G->>P: execute / upload / download
    activate P
    Note right of P: 持有 RLock

    SM->>P: replace_backend(NEW)
    Note right of SM: 等待同一把锁，排空在途操作

    P->>OLD: close()
    P->>P: _backend = NEW
    P-->>SM: 替换完成
    deactivate P

    G->>P: 下一次工具调用
    P->>NEW: 转发
```

**看图要点**

- 图里只持有 proxy，不持有具体 backend；因此替换不需要重建图。
- 替换是“排空在途操作后替换”，不是打断式替换。
- `close()` 关闭的是旧客户端，不是远端持久化沙箱。

### 8.1 `CompositeBackend` 路由

```mermaid
flowchart LR
```

**路由语义**

### 8.2 技能增量同步时序

```mermaid
sequenceDiagram
    autonumber
    participant MW as SandboxSkillsMiddleware
    participant S as SandboxSkillSynchronizer
    participant L as 宿主 skills/
    participant P as SandboxBackendProxy
    participant SB as 沙箱

    MW->>S: sync(proxy)
    S->>S: 获取 SKILL_PERSISTENCE_LOCK
    S->>P: transaction() 持有代理锁
    S->>L: 读取 skills/ + AGENTS.md
    S->>S: 计算每个文件 sha256
    S->>P: download /.myagent/skills-manifest.json
    P-->>S: 旧 manifest 或 file_not_found

    S->>S: changed = 内容不同的文件
    S->>S: removed = 旧 manifest 有、本地已删除的文件

    alt 有变更
        S->>P: upload 变更文件
        S->>SB: rm 已删除文件
        S->>P: 最后写 manifest
        Note right of S: manifest 是提交标记
        S-->>MW: true
    else 无变更
        S-->>MW: false
    end
```

**为什么 manifest 最后写**

如果先写 manifest 再传文件，中途失败会留下“索引认为已同步、实际文件缺失”的状态。
最后写 manifest，失败时下次仍会检测到差异并重传。

## 9. 技能分配的双端事务

```mermaid
flowchart TD
    START["assign_skill(skill, target)"] --> UPLOAD["上传可信 runtime.zip 到沙箱"]
    UPLOAD --> SYNC["synchronize：宿主技能树增量同步到沙箱"]
    SYNC --> DISPATCH["沙箱 dispatch(assign)"]
    DISPATCH --> SNAP["沙箱建事务快照"]
    SNAP --> MOVE["移动 main/skill → subagents/target/skill"]
    MOVE --> MANIFEST["返回新目录 manifest"]

    MANIFEST --> EXPORT["宿主下载文件并逐文件校验"]
    EXPORT --> VERIFY{"size + sha256 一致?"}
    VERIFY -->|"否"| ROLLBACK["双端回滚"]
    VERIFY -->|"是"| PATH{"POSIX / Windows 路径校验通过?"}
    PATH -->|"否"| ROLLBACK
    PATH -->|"是"| META{"SKILL.md 与 metadata.json 一致?"}
    META -->|"否"| ROLLBACK
    META -->|"是"| BACKUP["宿主旧目录移入临时区"]
    BACKUP --> PUBLISH["宿主发布新目录"]
    PUBLISH --> FINISH["沙箱 finish 确认提交"]
    FINISH --> RELEASE["沙箱 release 清理快照"]
    RELEASE --> DONE["返回成功"]
    FINISH -->|"失败"| ROLLBACK
    BACKUP -->|"失败"| ROLLBACK

    ROLLBACK --> HOST["宿主快照复位"]
    ROLLBACK --> SBOX["沙箱 rollback"]
    SBOX -->|"回滚失败"| TOKEN["报告事务 token，需人工恢复"]
```

**看图要点**

- `download` 只在沙箱发生，不写宿主；此时还没有持久化。
- `assign / update / delete` 才是双端事务。
- 任一步失败先尝试两端回滚；`release` 失败只告警，因为两端已经提交，不能单边撤销。
- `skill-management` 是保留技能，不能 assign 或 delete。

### 10.2 上下文压缩的三条路径

```mermaid
flowchart LR
    A["工具结果"] --> B{"超过 20k token?"}
    B -->|"是"| C["自动 Offloading<br/>落盘，只留路径 + 前 10 行"]
    B -->|"否"| D["正常进入上下文"]

    E["对话历史"] --> F{"达到窗口 85%?"}
```

**看图要点**

- 自动摘要与主动压缩共享同一个 summarizer 实例，避免两套摘要上下文产生偏差。
- 压缩不是“丢历史”：完整历史仍在 checkpoint，摘要只是模型当前看到的部分。
- 记忆只写 `/memories/`，压缩摘要不写用户偏好文件。

## 11. 中间件钩子顺序

```mermaid
flowchart LR
    REQ["一次 Agent run"] --> SS["SandboxSkillsMiddleware<br/>abefore_agent"]

    SS --> CI["进入模型循环"]

    subgraph LOOP["模型循环"]
        direction LR
        CI2["ContextInjection<br/>wrap_model_call"] --> ST["SummarizationTool<br/>wrap_model_call"]
        ST --> SUM["Summarization<br/>before_model"]
        SUM --> MCL["ModelCallLimit<br/>before / after_model"]
        MCL --> LLM["模型"]
        LLM --> TCL["ToolCallLimit<br/>wrap_tool_call"]
        TCL --> TOOLS["工具执行"]
        TOOLS --> LLM
        LLM --> LOOP_END["退出模型循环"]
    end

    CI --> CI2
    LOOP_END --> MU["MemoryUpdateMiddleware<br/>aafter_agent"]
    MU --> RESP["返回用户"]

    REQ -.->|"顺序语义"| NOTE1["before_*：按声明顺序"]
    RESP -.->|"顺序语义"| NOTE2["after_*：按声明反序"]
```

**记住三条规则**

1. `before_*` 按中间件声明顺序执行。
2. `after_*` 按声明反序执行。
3. `wrap_model_call` / `wrap_tool_call` 是洋葱模型：先声明的最外层，后执行内层。

这也是为什么 `MemoryUpdateMiddleware` 放在最后声明：它需要在本轮回答完成后才执行。

## 12. 数据归属与隔离

| 数据 | 存储位置 | Key / Namespace | 隔离维度 |
|:--|:--|:--|:--|
| 图执行状态 / 消息历史 | PostgreSQL Checkpointer | `thread_id` | 会话 |
| 用户偏好 | PostgreSQL Store | `(user_id,)` + `/{user_id}/preferences.md` | 用户 |
| 会话索引（侧边栏） | PostgreSQL Store | `("sessions", user_id)` + `thread_id` | 用户 |
| 异步任务归属 | PostgreSQL Store | `("async_tasks",)` + `task_id` | 任务 |
| 沙箱 ID | PostgreSQL Store | `("sandboxes", user_id)` + `current` | 用户 |
| 技能权威副本 | 宿主磁盘 | `src/agent/skills/` | 项目 |
| 技能运行副本 | 沙箱 | `/skills/` | 用户沙箱 |
| Agent 图缓存 | 进程内存 | `user_id` | 用户 / 单进程 |

**边界**

- 同一用户多会话：共享 Agent 图与沙箱代理，但 checkpoint 按 `thread_id` 隔离。
- 不同用户：Store namespace、沙箱、Agent 图都隔离。
- 多进程：进程内缓存与会话锁不共享；当前只支持单 worker。

## 14. 常见理解误区

| 误区 | 实际 |
|:--|:--|
| “每个 Agent 一个沙箱” | 按 `user_id` 一个沙箱；多个会话共用 |
| “换沙箱要重建 Agent 图” | 图持有 proxy，只替换内部 backend |
| “异步子 Agent 是 Python 协程” | 它是独立 thread/run/status 的远程任务 |
| “`assign` 是复制技能” | 是移动语义，宿主上只保留一份 |
| “`/memories/` 是宿主文件” | 是虚拟路径，真实落点是 PostgreSQL Store |
| “工具结果超过上下文就直接截断” | 先 offload 到文件，再保留路径与预览 |
| “中断恢复用流里的第一个 interrupt id” | 必须用根图 checkpoint 的 canonical id |
| “沙箱重启后要重新同步全部技能” | 按 manifest 增量同步，只传变更文件 |
| “异步任务结果由前端负责保存” | 服务端幂等写回主会话，前端只负责展示 |
