## wrap_model_call/wrap_tool_call

### 🧩 `request` 是什么？内部有哪些常用属性？

在 `wrap_tool_call` 钩子中，`request` 的类型是 **`ToolCallRequest`**。它是对一次**即将发生的工具调用**的完整封装，由框架在**模型输出被解析、工具即将被执行之前**自动构造出来。

`ToolCallRequest` 的常用属性如下：

| 属性 | 类型 | 含义 |
| :--- | :--- | :--- |
| **`tool_call`** | `ToolCall` | **最核心的属性**，是一个字典，包含本次调用的 `name`（工具名）、`args`（参数）和 `id`（调用标识）。你的代码 `request.tool_call["name"]` 正是从这里取工具名。 |
| **`tool`** | `BaseTool` 或 `None` | 被调用的**工具实例**本身，可用于读取工具的元数据（如 description、schema）。如果工具是动态注册的，该属性可能为 `None`。 |
| **`state`** | `AgentState` | Agent 的**当前状态**，包含消息历史等内置状态，以及中间件可能扩展的状态字段。 |
| **`runtime`** | `Runtime` | **运行时上下文**，提供 metadata、signal、writer、interrupt 等运行时能力。 |

框架生成这个请求的时机非常明确：**当模型返回的响应中包含工具调用意图时**，工具节点（ToolNode）在真正执行工具之前，会先构造出 `ToolCallRequest`，然后将其依次传递给注册的 `wrap_tool_call` 中间件。

---

### 🎯 `handler` 是什么？是框架内部的委托吗？

是的，可以把它理解为一个**框架提供的委托（callback）**。它是 **“实际的工具执行逻辑”** 的抽象封装。

在 `wrap_tool_call` 的签名中，`handler` 的类型是 `Callable[[ToolCallRequest], ToolMessage | Command[Any]]`。框架会将真正的工具执行函数作为 `handler` 传入你的中间件。你**调用 `handler(request)` 的那一刻**，框架才会去执行真正的工具代码。

这种设计赋予了你完全的**控制权**：
- **正常调用**：`handler(request)` → 执行工具。
- **短路**：不调用 `handler`，直接返回一个伪造的 `ToolMessage`，工具就不会被执行。
- **重试**：在 `try/except` 中多次调用 `handler(request)`。
- **修改请求**：调用 `handler(request.override(...))` 来改变工具或参数后再执行。

所以，`handler` 不是你实现的逻辑，而是框架交给你的一把“钥匙”，用来触发后续的真实执行流。

---

### 📜 `Callable[[ToolCallRequest], ToolMessage | Command]` 怎么读？

这是 Python 的 `typing.Callable` 类型注解，用来描述**一个可调用对象（函数、方法等）的输入与输出类型**。

拆开来看：

- **`Callable`**：表示“可调用”。
- **`[...]`**：第一个列表描述**输入参数的类型**。
- **`[[ToolCallRequest]]`**：表示这个可调用对象接受**一个位置参数**，其类型是 `ToolCallRequest`。
- **`-> ToolMessage | Command`**（位于 `Callable[...]` 的末尾）：表示这个可调用对象的**返回值类型**，可以是 `ToolMessage`，也可以是 `Command`（联合类型 `|` 表示“或”）。

连起来读就是：**“`handler` 是一个函数，你给它一个 `ToolCallRequest`，它会返回一个 `ToolMessage` 或 `Command`。”**

对应到你的代码：`handler(request)` 就是在调用这个函数，把当前的请求交还给框架，框架执行完工具后，会返回一个 `ToolMessage`（工具执行结果）或 `Command`（用于更新状态的指令），你再把这个结果原样返回即可。

### 💎 总结

你当前代码的逻辑（计数、计时、异常记录）本身是清晰且正确的，**唯一需要修正的是方法名**：将 `wrap_model_call` 改为 **`wrap_tool_call`**。这样，`ToolCallRequest`、`handler` 的类型注解，以及你内部对 `request.tool_call` 的访问，就全部对上了。如果确实还需要包装模型调用（比如统计模型调用次数），那需要另写一个 `wrap_model_call` 方法，使用 `ModelRequest` 和 `ModelResponse`，两者互不干扰。
